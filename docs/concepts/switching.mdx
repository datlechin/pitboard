title: "How switching works"
description: "Every switch parks the login in use and puts a parked one in its place, whoever starts it."
---

Claude Code and OpenAI's Codex CLI each read one stored login. Pitboard keeps every other account's login in its own store.

## Parked logins

A parked login is the login Pitboard holds for an account not in use. Each account has at most one.

Enrolling the account in use parks nothing: a copy would go stale as the tool renews its login. The first switch away parks it.

See [Where parked logins are kept](/security#where-parked-logins-are-kept) and [Why parked logins expire](/guides/renewal#why-parked-logins-expire).

## How Pitboard knows whose login it is

Pitboard moves no login until it identifies it: one filed under the wrong account would cost two accounts their login.

For Codex, it reads the account from the login itself, with no request, as read in Codex 0.154.0.

For Claude Code, it asks Anthropic, because the config can name another account. As read in Claude Code 2.1.294, a sign-in writes its account there. So does any process that starts while `profileFetchedAt` is missing or over 24 hours old. A switch removes that field, so a process started on another login, as over SSH, writes that login's account.

Pitboard records each answer with the login's fingerprint, and asks again only once that changes, as after a renewal or a sign-in. A switch and `pitboard forget` also ask once it has changed. Reads that send no request, such as `pitboard status --offline`, use the record.

Pitboard never asks Anthropic whose a login is with an expired access token. When it must ask and the login's access token has expired, it renews Claude Code's login first. Claude Code renews it only while a session uses it, and a [login file behind the keychain](#open-sessions) can keep every session off it.

Pitboard renews it as Claude Code does, as read in 2.1.294. It takes the lock a session takes to renew, and reads the login again under it. A login a session renewed meanwhile is asked about as it is. Otherwise Pitboard sends the refresh token, and saves the answer only where the stored login still holds that token.

Until the answer is saved, a copy waits in Pitboard's store. If Pitboard stops first or the save fails, the next change saves it, or the next read that must identify the login. While the copy waits, no change renews, parks, replaces or puts away that login. Each stops and says why the copy cannot be saved yet.

On macOS, Pitboard's store is the keychain that holds Claude Code's login. If the keychain is locked before Pitboard sends the refresh token, Pitboard sends nothing. Where macOS cannot ask for your password, as over SSH, a keychain that locks while Anthropic answers takes neither the copy nor the answer. The login stored then stops working. A change says so, and to run `claude` and sign in, and a read marks the account in use `login_refused`.

A read renews the login only while no other Pitboard command runs. Asking for usage never renews it, and a Codex login is never renewed this way.

If Anthropic no longer accepts the login, Pitboard changes nothing. A change stops with [`session_expired`](/reference/errors#switching), and a read marks the account in use `login_refused`.

When the config has named another account since Anthropic last answered, something may have signed in. Reads that send no request then warn with `in_use_unconfirmed`. `pitboard status` settles it, and the app starts such a read once by itself.

Pitboard also records each parked login's fingerprint, and refuses one that no longer matches.

## What a switch does

1. Takes Pitboard's own lock, `state.lock`, so one change runs at a time. Finishes or undoes any [interrupted switch](#interrupted-switches).
2. Identifies the login in use, renewing it first where its access token has expired.
3. Checks the incoming parked login with Anthropic or OpenAI, and renews it if it has lapsed. Every switch needs the network.
4. For Claude Code, takes the lock a session takes to renew its login, then Claude Code's write lock. No session can then renew the login being parked. Codex takes no lock.
5. Records the switch in `journal.json`, with fingerprints of both logins.
6. Parks the outgoing login: Claude Code's OAuth block and account entries, not its MCP server logins, or Codex's whole `auth.json`.
7. Reads the login in use again, and stops with `signed_in_account_changed` if it changed.
8. Writes the incoming login. On macOS, a failed keychain write never falls back to Claude Code's plaintext file.
9. Reads the login back and records the incoming account as in use, then releases Claude Code's locks. The read-back comes first because, as read in 2.1.284, a `/logout` that gives up waiting for the write lock deletes the login anyway.
10. For Claude Code, backs up the config to `~/.pitboard/backups/`, keeping 10 copies, then writes the incoming account into it without `profileFetchedAt`.

Pitboard waits about 7.5 seconds for a held Claude Code lock, then stops with `switch_in_progress`. As read in 2.1.294 and 2.1.284, Claude Code takes over a renewal lock after 60 untouched seconds and a write lock after 15.

## Who starts a switch

You start a switch in the app or with `pitboard use`. Pitboard starts one by itself only for Claude Code, while **Switch Claude Code automatically** is on in the app or `pitboard watch` runs. [Switch before an account runs out](/guides/automatic-switching) has the rules.

That switch runs the same steps, and `pitboard log` records it as `auto-switch`. Pitboard decides once under its lock, from the login and files as they are then. Two runs reading the same numbers make one switch.

Pitboard records each try in `autoswitch.json` before anything moves. A try stopped partway still counts.

## Open sessions

An open Claude Code session follows a switch within about 33 seconds, with no restart. It caches its login for 30 seconds, plus 3 for its next read. On one Mac with Claude Code 2.1.278, switches made 8, 20 and 28 seconds into a session took effect 32.3 to 33.5 seconds in.

Until then the session uses the account it is leaving. As read in 2.1.294, its `/status` already names the account switched to, from the rewritten config. `/usage` and every request still use the login it holds.

As read in 2.1.284, sessions and the daemon that renews their login read it again under the write lock before writing. None can write the previous account back.

Not known: whether a request under way during a switch finishes, and what Claude Code does at a limit.

On macOS, a `/login` while the keychain is locked leaves a login file behind the keychain, `~/.claude/.credentials.json`. Any file there pins open sessions: a login, `{}` or a file Pitboard cannot read.

As read in 2.1.294 and not measured, a pinned session keeps its login until it renews it, 5 minutes before expiry, or restarts. Sessions started later use the account switched to.

A switch then says so in place of the 33 seconds. Other changes and reads warn with `fallback_login`. `pitboard status --offline` does not look for the file. [Claude Code over SSH uses another account](/troubleshooting#claude-code-over-ssh-uses-another-account) has the fix.

As read in Codex 0.154.0, everything that runs Codex holds its login in memory until it stops. None follows a switch, so Pitboard never switches Codex by itself. [What happens to open sessions](/guides/switch#what-happens-to-open-sessions) says what to restart.

## Why Codex logins are moved, not copied

As read in Codex 0.154.0, `codex login` and `codex logout` ask OpenAI to revoke the stored login. A copy beside the login in use would be revoked with it at your next sign-in or sign-out.

So a switch moves the outgoing login into Pitboard's store, and reads it back there before writing the incoming one. Finishing or undoing an interrupted switch, `pitboard abandon` and `pitboard repair` keep no copy of the login in use either.

## Interrupted switches

A crash or Control-C can stop a switch partway, leaving `journal.json` behind.

The next change finishes or undoes it first: `pitboard use`, `enroll`, `forget`, `rename`, `stow`, `repair`, `uninstall` or the same in the app. It compares the login in use with the journal's two fingerprints, with no request. `pitboard status`, `doctor`, `log` and `renew` leave it.

Pitboard does not switch by itself meanwhile: finishing it is your change to make.

A login matching neither fingerprint, usually one the tool renewed since, must be identified first, for Claude Code by Anthropic. Until then, every change stops without changing anything.

[Interrupted switches](/reference/errors#interrupted-switches) lists what Pitboard says meanwhile. [An interrupted switch cannot be finished](/troubleshooting/recovery#an-interrupted-switch-cannot-be-finished) says how to give up on it.
