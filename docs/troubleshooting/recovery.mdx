Most fixes here run on the command line. If you have only the app, first [put the bundled command line on your `PATH`](/install#put-the-bundled-command-line-on-your-path).

## An interrupted switch cannot be finished

Every command that changes something stops with an error (`recovery_undetermined`) saying an earlier switch `was interrupted, and Pitboard cannot yet tell whether it finished`. The app shows the notice **An interrupted switch is waiting**. [Error and warning codes](/reference/errors#interrupted-switches) lists every place it shows.

A switch stopped partway, for example in a crash or a power cut, and Pitboard cannot yet identify the tool's login. [How switching works](/concepts/switching#interrupted-switches) explains how the next change settles it.

Run the program the error names, `claude` or `codex`, once. Then try the change again. Pitboard finishes or undoes the interrupted switch first, and a warning says which.

If the error comes back, for example while you are offline, give up on the switch:

```sh
pitboard abandon
```

In the app, click **Give Up** in the notice, then **Give Up** again to confirm. Giving up keeps every login. Run `pitboard` to check which account each tool shows as `signed in`. [`abandon`](/reference/recovery-commands#abandon) shows what it prints.

If the error says `this run reads it from somewhere else` (`recovery_elsewhere`), the switch ran with a different `CLAUDE_CONFIG_DIR` or `CODEX_HOME`. Run the command again with that variable set as it was, or run `pitboard abandon`.

If the error says the record of the switch `is damaged` (`recovery_record_corrupt`), check that `pitboard` shows the account you expect as `signed in`. Then delete the file the error names, usually `~/.pitboard/journal.json`.

## Pitboard lost track of parked logins

After `~/.pitboard` is restored from a backup or loses files, `pitboard` can show `nothing parked` for an account whose [parked login](/concepts/switching#parked-logins) still exists.

Run `pitboard repair` before you sign in to that account again. A sign-in parks a fresh login for it, and `repair` gives nothing back to an account that already holds one.

```sh
pitboard repair
```

```text
Gave personal back a parked login that nothing named.
```

[`repair`](/reference/recovery-commands#repair) lists its other results.

On macOS, every Pitboard directory shares the keychain, so a login `repair` gives back may be another directory's. `pitboard forget` and `pitboard uninstall` leave such a login in the keychain until you switch to its account or Pitboard renews it.

## The Pitboard directory came from another computer

Migration Assistant or a backup can bring `~/.pitboard` from another computer. Pitboard refuses to use it. Commands stop with an error (`state_wrong_machine`) saying the account list `was written on another computer`. In the app, the **Accounts** pane shows **Couldn't Read Accounts** with the same message.

Run `pitboard adopt`. It keeps your accounts and drops the parked logins they came with.

```sh
pitboard adopt
```

It prints a line such as `pitboard enroll personal --sign-in` for each account whose parked login it dropped. Run each line, or sign in from the app as [Sign in to an account again](/guides/sign-in-again) shows.

[What Pitboard will not do](/concepts/limits#rules) says why a parked login never moves between computers.
