## What each release attests

An attestation is a signed record, kept by GitHub, of the workflow and commit that built a file. Every release attests these files:

- each command line tarball
- the app's zip file
- a CycloneDX bill of materials (`.cdx.json`) beside each tarball and the app
- `SHA256SUMS`, the checksums of the tarballs and the app
- `appcast.xml`, the feed the app updates from

A pre-release, tagged like `v0.10.0-rc1`, has no `appcast.xml`.

Checking an attestation needs the [GitHub CLI](https://cli.github.com), `gh`, signed in to a GitHub account.

## Check an attestation

In the download's folder, run this with the file's name:

```sh
gh attestation verify Pitboard-v0.10.0-macos.zip --repo datlechin/pitboard
```

When a workflow in `datlechin/pitboard` attested that exact file, `gh` prints `Verification succeeded!` and exits with status 0. A changed file has no attestation, and the command fails.

With `--repo` alone, `gh` accepts an attestation from any workflow in the repository. Add `--signer-workflow` to accept only the release workflow:

```sh
gh attestation verify Pitboard-v0.10.0-macos.zip --repo datlechin/pitboard \
  --signer-workflow datlechin/pitboard/.github/workflows/release.yml
```

## Check the checksums

Download `SHA256SUMS` from the same release and check its attestation first:

```sh
gh attestation verify SHA256SUMS --repo datlechin/pitboard
```

On its own, `SHA256SUMS` shows only that a download arrived whole. Anyone able to change the release could change a file and its checksum together.

Then, in the folder that holds both files, on macOS:

```sh
shasum -a 256 -c SHA256SUMS --ignore-missing
```

On Linux:

```sh
sha256sum -c SHA256SUMS --ignore-missing
```

`--ignore-missing` skips the files you did not download. A file that matches prints:

```text
Pitboard-v0.10.0-macos.zip: OK
```

A file that differs prints `FAILED`, and the command exits with status 1.

Homebrew checks the files it installs against the checksums the release workflow took. It refuses one changed on the release page later.

## Check the signature on macOS

The macOS command line and app are signed with a Developer ID and notarised by Apple. Files for Linux are not signed.

The app carries its notarisation ticket. Gatekeeper fetches the command line's ticket from Apple when you first open a copy downloaded in a browser.

`spctl` asks Gatekeeper whether macOS would open a file. For the app:

```sh
spctl --assess --type execute -v /Applications/Pitboard.app
```

```text
/Applications/Pitboard.app: accepted
source=Notarized Developer ID
```

For the command line, use `--type install`, since `--type execute` accepts only apps. In the folder the tarball unpacked into:

```sh
spctl --assess --type install -v pitboard
```

```text
pitboard: accepted
source=Notarized Developer ID
```

Any developer's notarised file is `accepted`. With `-vvv` in place of `-v`, an `origin` line names the signer. For Pitboard's files, it ends with the team identifier `(D7HJ5TFYCU)`.

For what else Pitboard protects against, see [Security and privacy](/security#what-pitboard-protects-against).
