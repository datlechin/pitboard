## `renew`

```text
Renew every parked login that is due, and nothing else

Usage: pitboard renew [OPTIONS]
```

A [parked login](/concepts/switching#parked-logins) is due when:

| Tool | Due when |
| --- | --- |
| Claude Code | Its access token has expired or expires within 2 minutes, or its refresh token expires within 3 days. |
| Codex | Its access token has expired or expires within 2 minutes. Pitboard records no refresh token expiry for a Codex login. |
| Claude Desktop | Never. Pitboard renews no Claude Desktop login. |

A parked login whose refresh token has expired is never due. Its account needs a [sign-in again](/guides/sign-in-again).

`pitboard status` without `--offline` renews too, by the access token rule alone.

`renew` asks Anthropic or OpenAI to renew each due parked login, with every request sent at once.

`renew` never renews a login a tool is using. A parked login that copies one is dropped instead, since renewing it would spend the refresh token the tool holds. That account needs no sign-in.

| Service answer | What happens | Logged outcome |
| --- | --- | --- |
| Renewed | The renewed login replaces the parked one. | `renewed` |
| Refused | The parked login is dropped. Its account needs a sign-in again. | `parked_login_refused` |
| Unreachable, or asked for less traffic | Nothing changes. The next run tries again. | `renewal_deferred` |
| Another error | `renew` goes on with the other parked logins. | The error code |

`renew` prints one line:

| Output | When |
| --- | --- |
| `No parked login was due.` | Nothing was due. |
| `No parked login was due.` | Nothing was tried: another Pitboard run is changing something, a switch is interrupted or the account list cannot be read. |
| `2 due; none could be renewed this time.` | No due parked login was renewed. |
| `Renewed one.` | The only due parked login was renewed. |
| `Renewed all 2.` | Every due parked login was renewed. |
| `Renewed 1 of 2; the rest are tried again next time.` | Some due parked logins were renewed. |

`renew` exits with status 0, even when nothing was renewed. Where Pitboard may change nothing, it fails with [`elevated`](/reference/errors#root-sudo-and-administrator) or [`system_too_old`](/reference/errors#windows).

```sh
pitboard renew
```

```text
Renewed all 2.
```

## `schedule`

```text
Keep parked logins alive without running anything yourself

Usage: pitboard schedule [OPTIONS] <COMMAND>
```

| Command | What it does | Output begins |
| --- | --- | --- |
| `install` | Writes the job, replacing one already there, and hands it to the system's scheduler. | `Parked logins will be renewed daily.`, then where the job is |
| `status` | Checks that the job is there, not whether it ran. | `Parked logins are renewed every 1d 0h by this computer's own scheduler.` or `Nothing is keeping parked logins alive here.` |
| `uninstall` | Stops the job and deletes what `install` wrote. | `Stopped renewing parked logins on a schedule.` or `There was nothing scheduled.` |

The job runs `pitboard renew` once a day, from the `pitboard` that installed it, by full path. If that file is gone, `pitboard doctor` fails its `schedule` check: see [Daily renewal stopped working](/troubleshooting/renewal#daily-renewal-stopped-working). [Renewal schedule](/reference/files#renewal-schedule) lists its files.

The job renews the parked logins in Pitboard's own directory, `~/.pitboard` or, on Windows, `%USERPROFILE%\AppData\Local\Pitboard`, whatever `PITBOARD_HOME` it is given. While `PITBOARD_HOME` names another directory, `install` refuses with `schedule_not_default_home`, and `status` says which directory the schedule renews. A link to the default directory counts as another directory. `uninstall` works whatever `PITBOARD_HOME` says.

The system starts the job without your shell's environment. `install` gives it each proxy variable it was started with: `ALL_PROXY`, `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY`, in either case. Run `install` again after your proxy changes. Until then, `pitboard doctor` warns with `schedule_proxy`. The app's **Renew parked logins daily** setting gives the job the app's variables, not your shell's: see [The schedule uses another proxy](/troubleshooting/renewal#the-schedule-uses-another-proxy).

<Tabs>
  <Tab title="macOS">
    A LaunchAgent runs the job every 24 hours, the first time 24 hours after `install`. launchd skips a run due while the Mac sleeps. `install` writes the proxy variables and `PITBOARD_NO_ARGV` into the job.

    `install` refuses with `schedule_refused` when the program's path or a variable holds a character a LaunchAgent cannot hold, and names it. It refuses with `schedule_program_temporary` when the program is in the temporary copy macOS makes of an app opened where it was downloaded.
  </Tab>
  <Tab title="Windows">
    A task in Task Scheduler, `\Pitboard\Renew <SID>`, runs the job each day at the time of day `install` ran, the first time a day later. It runs only while you are signed in to Windows, as you and not elevated, and stops after 10 minutes. Task Scheduler starts a run it missed as soon as it can.

    A task holds no environment, so `install` writes the proxy variables to `schedule.env` in Pitboard's directory, and each run reads them from there. `install` refuses with `schedule_program_temporary` when the program is in the temporary copy Windows makes of a zip it opened.
  </Tab>
  <Tab title="Linux">
    A systemd user timer runs the job 15 minutes after your user's systemd starts, then 24 hours after each run. `install` writes the proxy variables and `PITBOARD_NO_ARGV` into the job.
  </Tab>
</Tabs>

On a Mac:

```sh
pitboard schedule install
```

```text
Parked logins will be renewed daily.
/Users/me/Library/LaunchAgents/com.datlechin.pitboard.renew.plist

It renews your own parked logins and does nothing else: it never switches account and never asks Anthropic for usage.
```

On Windows, the second line is the task's path, such as `\Pitboard\Renew S-1-5-21-…`.

## `log`

```text
What Pitboard has changed, and when

Usage: pitboard log [OPTIONS]
```

| Option | Description |
| --- | --- |
| `-n, --lines <LINES>` | How many changes to show. 20 by default. |

`pitboard log` prints the most recent changes, oldest first. Each line gives the local time, a verb, the subject and the outcome. The outcome is `ok`, a code from the table, or the error code that stopped the change.

With nothing logged, it prints `Pitboard has not changed anything yet.`

Only `--json` says which front end made each change, in `caller`: `cli`, `app`, or `unknown` for older lines.

The log is `audit.log` in Pitboard's directory, and holds no email address. Past 256 KiB, Pitboard moves it to `audit.log.1`, replacing the one there, and `pitboard log` reads both.

| Verb | Written when | Subject | Outcome |
| --- | --- | --- | --- |
| `use` | A switch you make, or **Update Claude Code's Config** in the app. | The label | `ok`. `already_active` when the account was in use. `config_updated` when it was, and Pitboard wrote it into Claude Code's config. |
| `auto-switch` | Pitboard switches Claude Code by itself, or such a switch fails. | The label switched to, or none if it failed before one was chosen | `ok`, or the error code |
| `auto-stay` | Pitboard could not identify whose login Claude Code has stored. One line per try. | The account last known in use, or none | `not_identified` |
| `auto-stay` | A limit of the account in use reached the share, and Pitboard held back. One line per limit and reset. | The account in use | A code from [When it stays on the account](/reference/automatic-switching#when-it-stays-on-the-account) |
| `in-use` | A read or a change finds the tool signed in outside Pitboard. | The account it finds signed in, or none if it is not enrolled | `signed_in_outside` |
| `in-use` | The same, for a sign-out outside Pitboard. | None | `signed_out_outside` |
| `in-use` | The same, for an account whose only login was replaced. | That account | `login_replaced` |
| `enroll` | An enrolment, with or without `--sign-in`. | The label | `ok`, or `label_unusable` when the label was refused |
| `park` | A Claude Desktop sign-in, from `pitboard enroll desktop/<label> --sign-in` or the app, starts to wait. It parks the account in use first, where there is one. | The label signed in to | `ok`, or the error code |
| `forget` | An account is forgotten. | The label | `ok` |
| `rename` | A label changes. | Before and after: `wrong -> right` | `ok` |
| `stow` | `pitboard stow`, or **Clean Up** in the app. | The account the file's login was of, or none | What became of the login, as [`stow`](/reference/recovery-commands#stow) lists |
| `abandon`, `repair` | That command runs. | None | `ok` |
| `adopt` | `pitboard adopt` takes over a directory. | None | `ok` |
| `uninstall` | `pitboard uninstall` ran and Pitboard's directory is still there. | None | `ok`, or `parks_pending_removal` when a parked login could not be deleted |
| `renew` | `renew`, daily renewal, `status` or the app tries a due parked login. | The label | As the table in [`renew`](#renew) lists |
| `recover` | Pitboard finishes or undoes an interrupted switch before another change. | The label the switch was to | `interrupted_switch_finished` or `interrupted_switch_undone` |
| `reclaim` | A parked login is given back to its account. | The label | `ok` |
| `reclaim` | A parked login is discarded. | The parked login's name, which holds an account id | `discarded` |
| `schedule` | Daily renewal is turned on or off, or the app repairs a schedule that ran the app itself or a `pitboard` that is gone. | `install`, `uninstall` or `repair` | `ok` |
| `watch-service` | The watch service is installed or taken away. | `install` or `uninstall` | `ok` |
| `warm-up` | A warm-up runs, by itself or with `warm now` or **Warm Up Now**. | The label | `ok`, or a code from [Warm-up](/reference/errors#warm-up) |
| `warm-on`, `warm-off` | An account is turned on or off for warm-ups. | The label | `ok` |
| `warm-range` | The hours warm-ups are made in change. | The hours: `07:00-23:00` | `ok` |
| `config` | Pitboard removes keys that name another account from Claude Code's config. | The names of the keys | `dropped` |

```sh
pitboard log -n 3
```

```text
2026-09-22T09:14:03+07:00  enroll  personal  ok
2026-09-22T09:16:52+07:00  enroll  work  ok
2026-09-22T09:17:10+07:00  use     work  ok
```

## `uninstall`

```text
Delete every parked login this Pitboard wrote, the daily renewal schedule, the watch service and Pitboard's own files

Usage: pitboard uninstall [OPTIONS]
```

| Option | Description |
| --- | --- |
| `-y, --yes` | Do not ask first; needed without a terminal or with `--json`. |

While the Pitboard app is open, `pitboard uninstall` refuses with `pitboard_open` and deletes nothing: the app would make Pitboard's directory again. Quit it with **Quit Pitboard** on macOS, or **Exit** in its icon's menu on Windows. Otherwise it works in this order:

1. On macOS, where Pitboard holds a Claude Desktop login or a move of one waits, reads Claude's data folder as a change does, and settles the move. If it refuses, nothing is deleted.
2. Stops and removes the [watch service](/reference/account-commands#the-watch-service), then removes the daily renewal schedule. If either fails, it stops with nothing deleted.
3. Deletes every parked login this Pitboard wrote, and every folder set aside in `~/.pitboard/parks`.
4. Deletes Pitboard's directory, once every parked login and folder set aside is gone.

Step 1 stops with a code from [Claude Desktop](/reference/errors#claude-desktop), such as `app_open` or `uninstall_would_strand`.

The login each tool is using stays. On macOS, so do parked logins that `pitboard repair` gave back and this Pitboard did not write. The keychain is shared, so another Pitboard may own them.

While a warm-up runs, step 4 keeps the directory. It also keeps it where a file in it could not be removed, and names that file. Run `pitboard uninstall` again once the warm-up is over or the file is closed.

With `PITBOARD_HOME` set to another directory, it deletes that directory and leaves the schedule and the watch service. `pitboard schedule uninstall` and `pitboard watch uninstall` remove them. The question and the output name that directory.

While `CLAUDE_CODE_CUSTOM_OAUTH_URL` is set, `uninstall` refuses with `custom_oauth_endpoint`. [Custom OAuth endpoint](/reference/environment-variables#custom-oauth-endpoint) says why.

In a terminal, it asks first, as [Questions before deleting](/reference/commands#questions-before-deleting) describes:

```text
Delete every parked login this Pitboard wrote, the daily renewal schedule, the watch service and ~/.pitboard? Each tool stays signed in to the account in use; the others need signing in again. [y/N]
```

Anywhere else, such as in a script or with `--json`, it needs `--yes`. Without it, `uninstall` refuses with `confirmation_needed`, exit status 2, and changes nothing.

With two parked logins and daily renewal on:

```sh
pitboard uninstall --yes
```

```text
Removed 2 parked login(s). The login each tool is signed in with is untouched.
Turned off the daily renewal schedule.
~/.pitboard is gone. Remove Pitboard itself the way you installed it.
```

| Output | When |
| --- | --- |
| `Deleted 2 folder(s) set aside.` | On macOS, folders were set aside in `~/.pitboard/parks`. It follows the first line. |
| `Stopped the watch service.` | The watch service was installed. It comes before the schedule's line. |
| `` Left 1 parked login(s) that `pitboard repair` found and this Pitboard did not write, because they may be another Pitboard's. `` | macOS only. |
| `` 1 could not be deleted yet, so ~/.pitboard was kept; run `pitboard uninstall` again. `` | A parked login or a folder set aside could not be deleted, or a renewal of Claude Code's login could not be saved yet. It takes the place of the last line. |

On Windows, the question and the output name the directory by its path, such as `C:\Users\me\AppData\Local\Pitboard`.

[Remove Pitboard](/install/remove) has the whole removal.

## `doctor`

```text
Check that what Pitboard relies on still holds on this machine

Usage: pitboard doctor [OPTIONS]
```

`pitboard doctor` prints one line per check: a mark, the check's name and what it found. A line of advice follows where there is something to do. `doctor` changes nothing and sends no request.

| Mark | `level` in JSON | Meaning |
| --- | --- | --- |
| `✓` | `ok` | The check holds. |
| `!` | `warn` | Worth a look. Nothing is broken. |
| `✗` | `fail` | Something Pitboard relies on does not hold. |

The last line sums up:

| Last line | When |
| --- | --- |
| `Everything Pitboard checks is in order.` | Every check holds. |
| `One thing is worth looking at.` | One check warns and none fails. |
| `2 things are worth looking at.` | More than one check warns and none fails. |
| `1 broken: do not switch accounts until fixed.` | At least one check fails, and the number counts them. |

`doctor` exits with status 3 when a check fails, and 0 otherwise. With `--json`, a failed check also sets `ok` to `false` and the error code to `checks_failed`. `data` still holds every check, as [Data by command](/reference/json-output#data-by-command) lists.

`--json` writes your home folder as `~`, and replaces each of these with a digest of its kind, such as `<email 1a2b3c4d>`:

| Value | Kind |
| --- | --- |
| Email address | `email` |
| Your user name | `user` |
| Account id | `account` |
| Organisation id or name, Codex workspace id | `org` |
| Login fingerprint | `login` |
| Parked login name | `park` |
| A proxy's host and port, when not on loopback | `proxy` |
| Your Windows account's security identifier | `sid` |

On Windows, `--json` also writes your profile folder as `~` and your local app data folder as `%LOCALAPPDATA%`, and finds your user name and security identifier in any case.

Digests differ from one report to the next. Both reports write a proxy's user name and password as `***`. Otherwise the text report hides nothing.

`doctor` prints its own checks and Claude Code's first. Each other tool's checks follow under a heading, in this order:

| Heading | Shown when |
| --- | --- |
| `Codex` | Pitboard finds `codex`, Codex's directory, `~/.codex` or `CODEX_HOME`, exists, or a Codex account is enrolled |
| `Claude Desktop` | A Claude Desktop account is enrolled, or a folder is set aside |

When another tool's checks appear and Claude Code is absent, `doctor` leaves out `config_file`, `identity`, `in_use`, `slot`, `credential_size`, `credential_store`, `credential`, `fallback_login`, `storage_v5`, `claude_daemon`, `claude_version`, `status_line`, `auth_source` and `login_restrictions`. Claude Code is absent when it has no config file, no `claude` program and no stored login, and no Claude Code account is enrolled.

Some Codex levels depend on whether a Codex account is enrolled:

| Finding | Codex account enrolled | None enrolled |
| --- | --- | --- |
| Codex keeps its login outside `auth.json` | `fail` | `ok` |
| Pitboard cannot tell where Codex keeps its login | `fail` | `warn` |
| `auth.json` is absent | `warn` | `ok` |
| Codex is signed in some way other than a ChatGPT sign-in, such as an API key | `warn` | `ok` |
| The login in `auth.json` cannot be used | `fail` | `warn` |

On macOS, Claude Desktop's checks read the folders in `~/.pitboard/parks`, open no cookie and list no process. Once a Claude Desktop account is enrolled, they also read Claude's settings and the names at its data folder's first level.
