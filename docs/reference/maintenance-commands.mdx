## `renew`

```text
Renew every parked login that is due, and nothing else

Usage: pitboard renew [OPTIONS]
```

A [parked login](/concepts/switching#parked-logins) is due when:

| Tool | Due when |
| --- | --- |
| Claude Code | Its access token has expired or expires within 2 minutes, or its refresh token expires within 3 days. |
| Codex | Its access token has expired or expires within 2 minutes. Pitboard records no refresh token expiry for a Codex login. |

A parked login whose refresh token has expired is never due. Its account needs a [sign-in again](/guides/sign-in-again).

`pitboard status` without `--offline` renews too, by the access token rule alone.

`renew` asks Anthropic or OpenAI to renew each due parked login, with every request sent at once.

`renew` never renews a login a tool is using. A parked login that copies one is dropped instead, since renewing it would spend the refresh token the tool holds. That account needs no sign-in.

| Service answer | What happens | Logged outcome |
| --- | --- | --- |
| Renewed | The renewed login replaces the parked one. | `renewed` |
| Refused | The parked login is dropped. Its account needs a sign-in again. | `parked_login_refused` |
| Unreachable, or asked for less traffic | Nothing changes. The next run tries again. | `renewal_deferred` |
| Another error | `renew` goes on with the other parked logins. | The error code |

`renew` prints one line. **Renew Now** in **Settings** > **General** shows the same:

| Output | When |
| --- | --- |
| `No parked login was due.` | Nothing was due. |
| `No parked login was due.` | Nothing was tried: another Pitboard run is changing something, a switch is interrupted or the account list cannot be read. |
| `2 due; none could be renewed this time.` | No due parked login was renewed. |
| `Renewed one.` | The only due parked login was renewed. |
| `Renewed all 2.` | Every due parked login was renewed. |
| `Renewed 1 of 2; the rest are tried again next time.` | Some due parked logins were renewed. |

`renew` exits with status 0, even when nothing was renewed. As root or with `sudo`, it fails with `elevated`: see [Pitboard changes nothing as root](/troubleshooting#pitboard-changes-nothing-as-root).

```sh
pitboard renew
```

```text
Renewed all 2.
```

## `schedule`

```text
Keep parked logins alive without running anything yourself

Usage: pitboard schedule [OPTIONS] <COMMAND>
```

| Command | What it does | Output begins |
| --- | --- | --- |
| `install` | Writes the job, replacing one already there, and has launchd or systemd start it. | `Parked logins will be renewed daily.`, then the job's file |
| `status` | Checks only that the job's file exists, not whether launchd or systemd loaded it. | `Parked logins are renewed every 1d 0h by this computer's own scheduler.` or `Nothing is keeping parked logins alive here.` |
| `uninstall` | Stops the job and deletes its files. | `Stopped renewing parked logins on a schedule.` or `There was nothing scheduled.` |

The job runs `pitboard renew` every 24 hours: a LaunchAgent on macOS, a systemd user timer on Linux. [Renewal schedule](/reference/files#renewal-schedule) lists its files.

The job runs the `pitboard` that installed it, by full path. If that file is gone, `pitboard doctor` fails its `schedule` check: see [Daily renewal stopped working](/troubleshooting#daily-renewal-stopped-working).

The job renews the parked logins in `~/.pitboard`, whatever `PITBOARD_HOME` it is given.

While `PITBOARD_HOME` names another directory, `install` refuses with `schedule_not_default_home`, and `status` says the schedule renews only `~/.pitboard`. A link to `~/.pitboard` counts as another directory. `uninstall` works whatever `PITBOARD_HOME` says.

launchd and systemd start the job without your shell's environment. `install` copies into the job each proxy variable it was started with: `ALL_PROXY`, `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY`, in either case. It also copies `PITBOARD_NO_ARGV`.

Run `install` again after your proxy changes. Until then, `pitboard doctor` warns with `schedule_proxy`. The app's **Renew parked logins daily** setting gives the job the app's variables, not your shell's: see [The schedule uses another proxy](/troubleshooting#the-schedule-uses-another-proxy).

On macOS, `install` refuses with `schedule_refused` when the program's path or a variable holds a character a LaunchAgent cannot hold, and names it.

On a Mac:

```sh
pitboard schedule install
```

```text
Parked logins will be renewed daily.
/Users/me/Library/LaunchAgents/com.datlechin.pitboard.renew.plist

It renews your own parked logins and does nothing else: it never switches account and never asks Anthropic for usage.
```

## `log`

```text
What Pitboard has changed, and when

Usage: pitboard log [OPTIONS]
```

| Option | Description |
| --- | --- |
| `-n, --lines <LINES>` | How many changes to show. 20 by default. |

`pitboard log` prints the most recent changes, oldest first. Each line gives the local time, a verb, the subject and the outcome. The outcome is `ok`, a code from the table, or the error code that stopped the change.

With nothing logged, it prints `Pitboard has not changed anything yet.`

Only `--json` says which front end made each change, in `caller`: `cli`, `app`, or `unknown` for older lines.

The log is `~/.pitboard/audit.log`, and holds no email address. Past 256 KiB, Pitboard moves it to `audit.log.1`, replacing the one there, and `pitboard log` reads both.

| Verb | Written when | Subject | Outcome |
| --- | --- | --- | --- |
| `use` | A switch you make, or **Update Claude Code's Config** in the app. | The label | `ok`. `already_active` when the account was in use. `config_updated` when it was, and Pitboard wrote it into Claude Code's config. |
| `auto-switch` | Pitboard switches Claude Code by itself, or such a switch fails. | The label switched to, or none if it failed before one was chosen | `ok`, or the error code |
| `auto-stay` | Pitboard could not identify whose login Claude Code has stored. One line per try. | The account last known in use, or none | `not_identified` |
| `auto-stay` | A limit of the account in use reached the share, and Pitboard held back. One line per limit and reset. | The account in use | `no_room`, `already_switched`, `attempts_spent`, `settling` or `auth_overridden`, as [When it holds back](/guides/automatic-switching#when-it-holds-back) describes |
| `in-use` | A read or a change finds the tool signed in outside Pitboard. | The account it finds signed in, or none if it is not enrolled | `signed_in_outside` |
| `in-use` | The same, for a sign-out outside Pitboard. | None | `signed_out_outside` |
| `in-use` | The same, for an account whose only login was replaced. | That account | `login_replaced` |
| `enroll` | An enrolment, with or without `--sign-in`. | The label | `ok`, or `label_unusable` when the label was refused |
| `forget` | An account is forgotten. | The label | `ok` |
| `rename` | A label changes. | Before and after: `wrong -> right` | `ok` |
| `stow` | `pitboard stow`, or **Put Away** in the app. | The account the file's login was of, or none | What became of the login, as [`stow`](/reference/recovery-commands#stow) lists |
| `abandon`, `repair` | That command runs. | None | `ok` |
| `adopt` | `pitboard adopt` takes over a directory. | None | `ok` |
| `uninstall` | `pitboard uninstall` ran and `~/.pitboard` is still there. | None | `ok`, or `parks_pending_removal` when a parked login could not be deleted |
| `renew` | `renew`, daily renewal, `status` or the app tries a due parked login. | The label | As the table in [`renew`](#renew) lists |
| `recover` | Pitboard finishes or undoes an interrupted switch before another change. | The label the switch was to | `interrupted_switch_finished` or `interrupted_switch_undone` |
| `reclaim` | A parked login is given back to its account. | The label | `ok` |
| `reclaim` | A parked login is discarded. | The parked login's name, which holds an account id | `discarded` |
| `schedule` | Daily renewal is turned on or off, or the app repairs a schedule that ran the app itself. | `install`, `uninstall` or `repair` | `ok` |
| `config` | Pitboard removes keys that name another account from Claude Code's config. | The names of the keys | `dropped` |

```sh
pitboard log -n 3
```

```text
2026-09-22T09:14:03+07:00  enroll  personal  ok
2026-09-22T09:16:52+07:00  enroll  work  ok
2026-09-22T09:17:10+07:00  use     work  ok
```

## `uninstall`

```text
Delete every parked login this Pitboard wrote, the daily renewal schedule and Pitboard's own files

Usage: pitboard uninstall [OPTIONS]
```

| Option | Description |
| --- | --- |
| `-y, --yes` | Do not ask first. |

`pitboard uninstall` works in this order:

1. Removes the daily renewal schedule. If that fails, it stops with nothing deleted.
2. Deletes every parked login this Pitboard wrote.
3. Deletes `~/.pitboard`, once every parked login is gone.

The login each tool is using stays.

On macOS, it also leaves parked logins that `pitboard repair` gave back and this Pitboard did not write. The keychain is shared, so another Pitboard may own them.

With `PITBOARD_HOME` set to another directory, it deletes that directory and leaves the schedule. `pitboard schedule uninstall` removes the schedule. The question and the output still say `~/.pitboard`.

While `CLAUDE_CODE_CUSTOM_OAUTH_URL` is set, `uninstall` refuses with `custom_oauth_endpoint`. [Custom OAuth endpoint](/reference/files#custom-oauth-endpoint) says why.

In a terminal, it asks first, as [Questions before deleting](/reference/commands#questions-before-deleting) describes:

```text
Delete every parked login this Pitboard wrote, the daily renewal schedule and ~/.pitboard? The account you are signed in to stays signed in; the others need a browser sign-in again. [y/N]
```

With two parked logins and daily renewal on:

```sh
pitboard uninstall --yes
```

```text
Removed 2 parked login(s). The login each tool is signed in with is untouched.
Turned off the daily renewal schedule.
~/.pitboard is gone. Remove Pitboard itself the way you installed it.
```

| Output | When |
| --- | --- |
| `` Left 1 parked login(s) that `pitboard repair` found and this Pitboard did not write, because they may be another Pitboard's. `` | macOS only. |
| `` 1 could not be deleted yet, so ~/.pitboard was kept; run `pitboard uninstall` again. `` | A parked login could not be deleted, or a renewal of Claude Code's login could not be saved yet. It takes the place of the last line. |

[Remove Pitboard](/install/remove) has the whole removal.

## `doctor`

```text
Check that what Pitboard relies on still holds on this machine

Usage: pitboard doctor [OPTIONS]
```

`pitboard doctor` prints one line per check: a mark, the check's name and what it found. A line of advice follows where there is something to do. `doctor` changes nothing and sends no request.

| Mark | `level` in JSON | Meaning |
| --- | --- | --- |
| `✓` | `ok` | The check holds. |
| `!` | `warn` | Worth a look. Nothing is broken. |
| `✗` | `fail` | Something Pitboard relies on does not hold. |

The last line sums up, in the words that head the [This Mac pane](/reference/app#this-mac-pane) in the app.

| Last line | When |
| --- | --- |
| `Everything Pitboard checks is in order.` | Every check holds. |
| `One thing is worth looking at.` | One check warns and none fails. |
| `2 things are worth looking at.` | More than one check warns and none fails. |
| `1 broken: do not switch accounts until fixed.` | At least one check fails, and the number counts them. |

`doctor` exits with status 3 when a check fails, and 0 otherwise. With `--json`, a failed check also sets `ok` to `false` and the error code to `checks_failed`. `data` still holds every check, as [Data by command](/reference/json-output#data-by-command) lists.

`--json` writes your home folder as `~`, and replaces each of these with a digest of its kind, such as `<email 1a2b3c4d>`:

| Value | Kind |
| --- | --- |
| Email address | `email` |
| Your user name | `user` |
| Account id | `account` |
| Organisation id or name, Codex workspace id | `org` |
| Login fingerprint | `login` |
| Parked login name | `park` |
| A proxy's host and port, when not on loopback | `proxy` |

Digests differ from one report to the next. Both reports write a proxy's user name and password as `***`. Otherwise the text report hides nothing.

Codex's checks come last, under the heading `Codex`. They appear when Codex's directory, `~/.codex` or `CODEX_HOME`, exists, or a Codex account is enrolled. Some levels depend on whether one is:

| Finding | Codex account enrolled | None enrolled |
| --- | --- | --- |
| Codex keeps its login outside `auth.json` | `fail` | `ok` |
| Pitboard cannot tell where Codex keeps its login | `fail` | `warn` |
| `auth.json` is absent | `warn` | `ok` |
| Codex is signed in some way other than a ChatGPT sign-in, such as an API key | `warn` | `ok` |
| The login in `auth.json` cannot be used | `fail` | `warn` |

When Codex's checks appear and Claude Code is absent, `doctor` leaves out `config_file`, `identity`, `in_use`, `slot`, `credential_size`, `credential_store`, `credential`, `fallback_login`, `storage_v5` and `claude_version`. Claude Code is absent when it has no config file, no `claude` program and no stored login, and no Claude Code account is enrolled.
