## `statusline`

```text
One line for Claude Code's status bar; reads its session JSON on stdin

Usage: pitboard statusline [OPTIONS]
```

It uses these fields of the session JSON:

| Field | Use |
| --- | --- |
| `session_id` | Compares this run with the session's last one. Without it, Pitboard records nothing. |
| `rate_limits.five_hour.used_percentage`, `rate_limits.five_hour.resets_at` | The five-hour limit |
| `rate_limits.seven_day.used_percentage`, `rate_limits.seven_day.resets_at` | The weekly limit |

When standard input is a terminal, it reads nothing. Input that is not JSON counts as empty.

It prints the session's account, then every other enrolled Claude Code account, two spaces apart. Limits for a single model and accounts of OpenAI's Codex CLI never appear.

| Value | Meaning |
| --- | --- |
| `46%·70%` | 46% of the five-hour limit and 70% of the weekly limit are used. Whole numbers, a half rounded up. |
| `?` | Pitboard has no reading of that limit. |
| `20%` alone | The account has only the five-hour limit of the two, as a Team seat has no weekly limit for all models. |
| `0%` | None of that limit is used, or its period has reset since Pitboard's reading. |
| `▲` | First account only: that limit is used faster than an even [pace](/concepts/usage#pace). |
| `▼` | First account only: that limit is used slower than an even pace. |
| No triangle | On pace, or no pace for that limit. |
| `(3h 00m)` | The age of another account's reading, once older than 15 minutes. The first account never shows one. |

The first label comes from the session's periods when they [identify its account](#which-account-a-session-records-for). Otherwise it comes from the account in use: Pitboard's [record](/concepts/identity) of Anthropic's last answer about Claude Code's login.

That record is unconfirmed before Pitboard first asks, and while Claude Code's config names another account than at that answer. `pitboard status` confirms it.

| First label | When | Percentages |
| --- | --- | --- |
| `work` | The session's periods identify `work`. | `work`'s reading |
| `work` | The session passed no running period. `work` is in use, confirmed. | `work`'s reading |
| `work?` | The same, unconfirmed. | `work`'s reading |
| `work?` | The session's running periods identify no account, or several. `work` is in use. | The session's own |
| `?` | The same, but `work`'s reading rules the session out. It holds another running period of a limit the session passed, or lists every limit `work` has without that one. | The session's own |
| `?` | The session's periods identify no account. The record names no enrolled account, unconfirmed. | The session's own |
| `unenrolled` | The same, confirmed: Claude Code's login is an account you have not enrolled, or there is none. | The session's own |

| Part | Style |
| --- | --- |
| The first account's label, or `unenrolled` | Bold |
| Other labels, `·`, `?` and ages | Dim |
| A percentage | Green under 70%, yellow from 70%, red from 90% |
| `▲` | Red |
| `▼` | Green |

Without `NO_COLOR`, the line has colour through a pipe too. With `NO_COLOR` set, even to an empty value, it follows the [colour rules](/reference/commands#output) of other commands.

With `--json`, [`data.line`](/reference/json-output#data-by-command) holds the line without colour.

It sends no request and never reads the keychain, Credential Manager or a login. It reads Pitboard's own files, and Claude Code's config only to check whether the record is unconfirmed.

It writes two files in the [Pitboard directory](/reference/files#the-pitboard-directory):

| File | What it writes |
| --- | --- |
| `sessions.json` | What each session passed at its last run |
| `usage.json` | Limits that moved since the session's last run, into the reading of the account its periods identify |

### Which account a session records for

The session's numbers name no account (read in Claude Code 2.1.294), but each account's periods reset at their own times. Pitboard records them for the one enrolled account whose reading holds a period the session passed, to within a minute, asking no service.

A reading with another running period of one of those limits does not match. Nor does one that lists every limit but lacks one passed. With no match, or several, Pitboard records nothing. So an [open session](/concepts/open-sessions) still on its old account after a switch records there until it follows.

A five-hour period begun since Pitboard last asked Anthropic matches no reading, so the weekly period passed with it identifies the account. A Team seat's session passes only its five-hour limit, and records nothing after a reset until Pitboard asks again.

One risk is known. A session on an account no reading holds, such as an unenrolled one, can pass a five-hour period that resets within a minute of an enrolled account's. Its numbers then record for that account, and each answer from Anthropic corrects them only until the session's next response. The session's weekly period prevents this when that account's reading holds a different one, or no weekly limit for all models.

A session's numbers only move a limit the account's last answer from Anthropic gave. Once that limit resets, they start its next period. Pitboard records only limits that moved since the session's last run. An idle session passes the same numbers again, which can predate an answer that lowered a percentage.

Where a change fails with [`elevated`](/reference/errors#root-sudo-and-administrator) or [`system_too_old`](/reference/errors#windows), it writes nothing.

It exits 0 whatever its input. When a home variable is empty or not a full path, it prints no line and exits 1 with [`home_not_absolute`](/reference/errors#the-pitboard-directory).

At a prompt, it prints Pitboard's last readings:

```sh
pitboard statusline
```

```text
work 46%·70%  personal 12%·40%  side ?·? (3h 00m)
```

[Show usage in Claude Code's status line](/guides/status-line) adds it to Claude Code, and says which shell runs it on Windows.

## `completions`

```text
Print a shell completion script

Usage: pitboard completions [OPTIONS] <SHELL>
```

| Argument | Values |
| --- | --- |
| `<SHELL>` | `bash`, `elvish`, `fish`, `powershell`, `zsh` |

It writes the script to standard output. With `--json`, it prints no script and exits 2 with [`output_is_not_a_report`](/reference/errors#command-output).

| Install | Scripts |
| --- | --- |
| The install script | `bash-completion/completions/pitboard`, `zsh/site-functions/_pitboard` and `fish/vendor_completions.d/pitboard.fish`, under `~/.local/share` |
| Either Homebrew cask | `etc/bash_completion.d/pitboard`, `share/zsh/site-functions/_pitboard` and `share/fish/vendor_completions.d/pitboard.fish`, under `$(brew --prefix)` |
| Release tarball | `completions/pitboard.bash`, `pitboard.zsh` and `pitboard.fish` |
| The macOS app | The same three files in `Pitboard.app/Contents/Resources/completions/` |
| Windows zip | `completions/pitboard.ps1` and `completions/pitboard.bash`, for PowerShell and Git Bash |
| The Windows app | `completions\pitboard.ps1` in `%LOCALAPPDATA%\Programs\Pitboard` |

No release includes the elvish script.

bash-completion 2.2 or later and fish 4 load the install script's files from those folders. zsh loads its file once `~/.zshrc` has these lines:

```sh
fpath=(~/.local/share/zsh/site-functions $fpath)
autoload -Uz compinit && compinit
```

Where `~/.zshrc` already runs `compinit`, add only the first line, before it.

zsh 5.9 on macOS 27 and on Debian 13 does not have that folder on its `fpath`, as measured on 12 October 2026.

zsh loads `_pitboard` from any folder on its `fpath`:

```sh
mkdir -p ~/.zfunc
pitboard completions zsh > ~/.zfunc/_pitboard
```

Then add the same two lines to `~/.zshrc`, with `~/.zfunc` as the folder.

PowerShell loads the script from your profile. In Windows PowerShell 5.1, add it only once [its execution policy](https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_execution_policies) is `RemoteSigned`: under `Restricted`, its default on Windows 11, it runs no profile.

In each PowerShell you use, add the app's script to the file `$PROFILE` names:

```powershell
if (-not (Test-Path $PROFILE)) { New-Item -ItemType File -Path $PROFILE -Force }
Add-Content -Path $PROFILE -Value '. "$env:LOCALAPPDATA\Programs\Pitboard\completions\pitboard.ps1"'
```

From a zip, name the `completions\pitboard.ps1` in the folder you unpacked it to, and run `Unblock-File` on that file first. PowerShell 7's default execution policy, `RemoteSigned`, refuses a script marked as downloaded from the internet, and File Explorer marks each file it extracts from a downloaded zip.

## `manpage`

```text
Print the man page

Usage: pitboard manpage [OPTIONS]
```

It writes roff to standard output. With `--json`, it exits 2 with `output_is_not_a_report`.

It is one page, with the sections `NAME`, `SYNOPSIS`, `DESCRIPTION`, `OPTIONS`, `COMMANDS` and `VERSION`. `COMMANDS` gives every command but `help` and `manpage`, each with its arguments and options.

| Install | Man page |
| --- | --- |
| The install script | `~/.local/share/man/man1/pitboard.1` |
| Either Homebrew cask | `share/man/man1/pitboard.1`, under `$(brew --prefix)` |
| Release tarball | `pitboard.1` |
| The macOS app | `Pitboard.app/Contents/Resources/man/pitboard.1` |

No Windows release includes the man page.

`man` finds the install script's page while `~/.local/bin` is on your `PATH`, on macOS and with man-db.

To read it without installing it:

```sh
pitboard manpage > pitboard.1
man ./pitboard.1
```
