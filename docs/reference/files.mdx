Paths here are defaults. [Environment variables](/reference/environment-variables) can move them. `~` is your home: the folder `HOME` names, or `USERPROFILE` on Windows.

## The Pitboard directory

Pitboard's directory is `~/.pitboard`, or the path in `PITBOARD_HOME`. The command line and the app share it.

On Windows, it is `%USERPROFILE%\AppData\Local\Pitboard`, whatever `LOCALAPPDATA` names.

Pitboard creates each directory at mode 0700 and each file at 0600. On Windows, it gives each an access list that admits only you, SYSTEM and Administrators. A directory that already exists keeps its own. A copy in `backups/` keeps the access of Claude Code's config.

| File | Holds | Written or taken by |
| --- | --- | --- |
| `state.json` | The enrolled accounts with their email addresses, ids and plans, their parked logins' names and expiry, whose login each tool has stored, a renewal of Claude Code's login not saved yet, a Claude Desktop move under way, a sign-in inside Claude left halfway, and which folders in `parks/` are set aside | Every change and renewal, and a read that finds a tool's stored login changed or an account's plan different from the one recorded |
| `state.lock` | The lock that lets one change run at a time | As `state.json`, and every automatic switch |
| `journal.json` | The record of a Claude Code or Codex switch until it is done. One left behind marks an [interrupted switch](/concepts/switching#interrupted-switches). | A switch |
| `pending` | Names of parked logins about to be written, one per line, which the next change resolves. A line for a folder in `parks/` starts with `folder `. Absent when empty. | Anything that parks a login |
| `autoswitch.json` | What the automatic switch tried and said at each limit, until a minute after it resets, or 7 days with no reset known. When it last failed to identify Claude Code's login. | The automatic switch |
| `signin.lock` | The lock that allows one sign-in at a time | A sign-in |
| `warm.json` | The accounts turned on for warm-ups, by id, and the hours they are made in | `pitboard warm on`, `off` and `range`, and the app's **Warm up limits** |
| `warmed.json` | The warm-ups of each account tried today, and when one last started its period | A warm-up |
| `warm.lock` | The lock that allows one warm-up at a time | A warm-up |
| `warm/` | Where Claude Code runs a warm-up, in `warm/claude/`, with a home and config of its own made for the run and removed after it. | A warm-up |
| `signin/` | Where a tool signs in, apart from the login in use. Removed when the sign-in ends, or by the next one. | A sign-in |
| `vault/` | Linux and Windows: the parked logins of Claude Code and Codex, one file each, sealed to your Windows account on Windows | Anything that parks or renews a login |
| `parks/` | macOS: the parked logins of Claude Desktop and the folders set aside, one folder each, as [Folders in parks](/reference/files#folders-in-parks) lists | A change to a Claude Desktop account, `repair` and `adopt` |
| `usage.json` | The newest usage reading of each account | Reading usage, and the status line |
| `usage.lock` | The lock around `usage.json` and `sessions.json` | As `usage.json` |
| `asking.json` | When Pitboard last asked Anthropic or OpenAI about each account, and any wait before it asks again. After a service asks for less traffic, the wait is the time it names, or else 1 minute, doubling up to 1 hour. After no answer or a server error, it is 30 seconds, doubling up to 15 minutes. | Reading usage |
| `sessions.json` | What each Claude Code session last passed the status line. A session unseen for 7 days is dropped. | The status line |
| `backups/` | Claude Code's config as it was before Pitboard rewrote it, named `claude.json.<seconds since 1970>`. The 10 newest stay. | A Claude Code switch, and `pitboard use` of the account in use where the config names another |
| `audit.log`, `audit.log.1` | The activity log that [`pitboard log`](/reference/maintenance-commands#log) prints, and the one before it | Every change, renewal and automatic switch, and a read that finds a sign-in outside Pitboard |
| `app.json` | The app's preferences, listed in [The app](/reference/files#the-app) | The app |
| `told.json` | Each limit the app has notified you of, by account and limit, with its reset, and each account whose parked login it asked you to sign in to again | The app |
| `app.lock` | The lock the app holds while it is open, which `pitboard uninstall` refuses over | The app |
| `schedule.env` | Windows: the proxy variables daily renewal runs with, as [Renewal schedule](/reference/files#renewal-schedule) says | `pitboard schedule install` |
| `watch.env` | Windows: the proxy variables the watch service runs with, as [Watch service](/reference/files#watch-service) says | `pitboard watch install` |

Only `vault/`, `signin/` and `parks/` can hold a login. `backups/` holds your email address, account ids and the path of each project Claude Code has opened.

Pitboard refuses a directory that a sync client copies to other machines, with `state_on_synced_drive`. It reads the path with links resolved:

| Where in the path | Refused |
| --- | --- |
| Anywhere as written, or as a whole folder name in any case | `Dropbox`, `Google Drive`, `OneDrive`, `com~apple~CloudDocs`, `Sync` |
| A folder named like these, in any case | `OneDrive - <organisation>`, `OneDrive-<kind>`, `Dropbox (<team>)`, `GoogleDrive-<account>` |
| Two adjacent folders, in any case | `Library/CloudStorage`, `Library/Mobile Documents` |
| Windows: inside a folder `OneDrive`, `OneDriveCommercial` or `OneDriveConsumer` names | That folder |
| Windows: inside a folder Windows syncs to the cloud | Any such folder |
| Windows: in a profile that roams, outside its `AppData\Local` and `AppData\LocalLow` | The profile |

Your home's own folders count, so `/home/sync/.pitboard` is refused.

## Parked logins

| Tool | System | A parked login is | Named |
| --- | --- | --- | --- |
| Claude Code, Codex | macOS | An item in your default keychain | `pitboard-park-<account id>-<time>` |
| Claude Code, Codex | Linux | A file in `~/.pitboard/vault/` | `pitboard-park-<account id>-<time>.json` |
| Claude Code, Codex | Windows | A file in `vault` in Pitboard's directory, sealed with Windows' data protection under your account | `pitboard-park-<account id>-<time>.json` |
| Claude Desktop | macOS | A folder in `~/.pitboard/parks/`, as [Folders in parks](/reference/files#folders-in-parks) lists | `pitboard-park-<account id>-<time>` |

On macOS, a keychain item's account is the one Claude Code's own item uses, from `USER`. Pitboard writes it through `/usr/bin/security`: on macOS 26, an item written through the Security framework takes about a second for each read by `security`, against 0.01 seconds.

When Pitboard renews Claude Code's login, a copy of the renewed login waits beside the parked logins as `pitboard-park-renewing-<time>` until it is saved where Claude Code keeps it.

`<account id>` is the id Pitboard gives the account at enrolment, which never changes:

| Tool | `<account id>` |
| --- | --- |
| Claude Code | The Anthropic account UUID and organisation UUID joined by `_`, or the account UUID alone for an older account |
| Codex | Built from the account's ChatGPT ids |
| Claude Desktop | `desktop_` and the account UUID Claude's settings named |

`<time>` is when the login was parked or last renewed, in milliseconds since 1 January 1970.

[Where parked logins are kept](/security#where-parked-logins-are-kept) says who can read them.

### Folders in parks

On macOS, each folder in `~/.pitboard/parks/` is a Claude Desktop parked login or a folder set aside. `state.json` records which folders are set aside. A folder set aside for an account stays until you forget that account or uninstall Pitboard. One that holds only what Claude made while signed out stays until `pitboard uninstall`.

| Folder | Named |
| --- | --- |
| A parked login | `pitboard-park-<account id>-<time>` |
| A parked login set aside | Its name as a parked login |
| A folder made for what a move set aside, such as what was in Claude's way | `pitboard-aside-<time>` |

Each folder holds:

| Path in the folder | What it is |
| --- | --- |
| `manifest.json` | The tool, the account, the account Claude's settings named, the session cookie's fingerprint and expiry, when it was parked, a hash of this Mac's identifier, the items, a SHA-256 digest of each key, and the items a give-up left in the data folder. Written before the first rename. |
| `keys.json` | The account's keys of `config.json`, as Claude wrote them. |
| `items/` | The login's items, under their names in Claude's data folder. |

## Claude Code files

Each place was read in Claude Code builds 2.1.278 to 2.1.309, and in 2.1.301 to 2.1.309 on Windows.

| Path | What Pitboard does with it |
| --- | --- |
| `~/.claude.json` | Read for the account it names: see [How Pitboard knows whose login it is](/concepts/identity). A Claude Code switch copies it to `backups/`, then writes the incoming account into it. A `.config.json` in Claude Code's config directory wins over it when that file is not empty. Where `~/.claude.json` is missing, an empty `.config.json` that is not read-only wins too. |
| Keychain item `Claude Code-credentials` | macOS: the login in use. A switch reads and replaces it. Pitboard writes a renewal of it where it must [identify it](/concepts/identity). |
| Credential Manager item `Claude Code-credentials/claude-code-user` | Windows, where Credential Manager is Claude Code's store: the login in use. A login too large for one item is kept in pieces beside it, `#m`, `#p`, then `#0` onward. A switch reads and replaces them. |
| `~/.claude/.credentials.json` | Linux: the login in use. A switch reads and replaces it. |
| `~/.claude/.credentials.json` | Windows, where it is Claude Code's store: the login in use. A switch reads and replaces it. |
| `~/.claude/.credentials.json` | macOS, and Windows where Credential Manager is Claude Code's store: a [login file behind the keychain or Credential Manager](/concepts/open-sessions#a-login-file-behind-the-keychain-or-credential-manager), read after it. Pitboard writes it only while the store holds no login. Otherwise only [`pitboard stow`](/reference/recovery-commands#stow) changes or deletes it, and the next change writes a renewal that a stopped `stow` left unsaved. |
| `~/.claude/.storage-write.lock` | The lock Claude Code takes around each write of its login. Pitboard takes it whenever it writes the login in use: a switch, a sign-in to the account in use, a renewal of it, and `pitboard stow`. |
| `~/.claude/.oauth_refresh.lock` and `~/.claude.lock` | The locks Claude Code takes, in that order, before it renews its login. Pitboard holds both through every Claude Code switch, `pitboard stow`, and each renewal of Claude Code's login. |
| `~/.claude/daemon.lock` | Read by `pitboard doctor` for the daemon Claude Code last started and its version. |
| `~/.claude/settings.json` | Read for `apiKeyHelper` and for an `env` block that sets a [variable Pitboard checks](/reference/environment-variables#variables-that-override-the-login), `CLAUDE_CODE_CUSTOM_OAUTH_URL` or, on Windows, `CLAUDE_CODE_FORCE_WINDOWS_CREDMAN`. There, `""`, `"0"` and `"false"` count as unset. A project's settings are not read. |
| `managed-settings.json` and `managed-settings.d/*.json` | Read as `settings.json` is, in `/Library/Application Support/ClaudeCode` on macOS, `C:\Program Files\ClaudeCode` on Windows or `/etc/claude-code` on Linux. Also read for `forceLoginMethod` and `forceLoginGatewayUrl`, which can send sessions through the Cloud gateway, and for `forceLoginOrgUUID`, which limits the organisations Claude Code signs in to. |
| `com.anthropic.claudecode.plist` in `/Library/Managed Preferences/<user>`, then in `/Library/Managed Preferences` | macOS: a configuration profile's managed settings. Read as `managed-settings.json` is, from the first that `plutil` can read, as read in 2.1.309. Never written. |
| `~/.config/anthropic/active_config` and `configs/*.json` beside it | Read for the [Anthropic profile](/reference/environment-variables#anthropic-profiles) Claude Code signs in with before the login. On Windows, in `%APPDATA%\Anthropic`. Never written. |
| A `user_oauth` profile's credentials file: `credentials/<name>.json` beside `configs`, or the profile's `credentials_path` | It holds that profile's login. Pitboard checks only that it is there and not empty. Never read or written. |
| The registry value `Settings` under `SOFTWARE\Policies\ClaudeCode` | Windows: read as `settings.json` is, in `HKEY_LOCAL_MACHINE` and in `HKEY_CURRENT_USER`. |
| `/home/claude/.claude/remote/.oauth_token` and `.api_key` | macOS and Linux: read for a token Claude Code signs in with before the login, as read in 2.1.303. While either holds one, changes to Claude Code accounts warn with `auth_overridden`, and while `.api_key` holds one, Pitboard [warms up](/guides/warm-up#when-it-holds-back) no account. Never written. |
| `\home\claude\.claude\remote\.oauth_token` and `.api_key` at the root of each fixed drive | Windows: read as `/home/claude/.claude/remote` is elsewhere, since Claude Code's path there names no drive. |

With `CLAUDE_CONFIG_DIR` or `CLAUDE_SECURESTORAGE_CONFIG_DIR` set, the keychain or Credential Manager item's name ends in `-` and the first 8 hex characters of the SHA-256 of that path as written.

Pitboard waits about 7.5 seconds for a held Claude Code lock, then stops with `switch_in_progress`. As read in 2.1.309 and 2.1.284, Claude Code takes over a renewal lock after 60 untouched seconds and a write lock after 15.

## Codex files

Each place was read in Codex 0.160.0, and in 0.163.0 on Windows.

| Path | What Pitboard does with it |
| --- | --- |
| `~/.codex/auth.json` | The login in use. A switch reads and replaces it. |
| `~/.codex/config.toml` | Read for the settings that choose Codex's login store and the logins it keeps. Never written. |

On Windows, Codex's home is `.codex` in the profile folder Windows names for your account, whatever `USERPROFILE` says, as read in Codex 0.162.1.

Pitboard switches Codex only while `auth.json` is its store, which `cli_auth_credentials_store` chooses. The `Codex login store` line of [`pitboard doctor`](/reference/maintenance-commands#doctor) names it. Each other store keeps the login elsewhere, as read in Codex 0.154.0 on macOS and in 0.163.0 on Windows:

| `Codex login store` | System | Where Codex keeps the login |
| --- | --- | --- |
| `keyring` | macOS, Linux | A keychain item Codex made for itself. |
| `keyring` | Windows | A Credential Manager item, while `secret_auth_storage` is off. |
| `auto` | macOS, Linux | The same keychain item, falling back to the file. |
| `auto` | Windows | The same Credential Manager item, falling back to the file, while `secret_auth_storage` is off. |
| `secrets` | macOS, Linux | An encrypted file whose key is in the keychain: `keyring` or `auto` with `secret_auth_storage` turned on in `[features]`. |
| `secrets` | Windows | `secrets\codex_auth.age` in Codex's home, whose key is in Credential Manager: `keyring` or `auto` while `secret_auth_storage` is on, as it is by default. |
| `ephemeral` | All | In memory, for one run of Codex. |

On macOS and Linux, Pitboard does not read Codex's keychain stores, because every read would ask you for permission. A login kept in memory leaves nothing to park.

Codex reads `cli_auth_credentials_store`, and `secret_auth_storage` under `[features]`, from these places, each over the one before:

1. Codex's own default, `file`.
2. The system's `config.toml`: `/etc/codex/config.toml`, or on Windows `config.toml` in `%ProgramData%\OpenAI\Codex`.
3. `config.toml` in `~/.codex` or `CODEX_HOME`.
4. On macOS and Linux, `/etc/codex/managed_config.toml`.
5. On macOS, the managed preference `config_toml_base64` of `com.openai.codex`, which a configuration profile sets.

The system's `requirements.toml`, in `/etc/codex` or in `%ProgramData%\OpenAI\Codex`, then on macOS the managed preference `requirements_toml_base64`, pin the store over all of them.

The `Codex login store` line of `pitboard doctor` names the place that chose. Codex does not start while one of them is there and unreadable. Pitboard then refuses with `live_store_unsupported`.

Pitboard reads a `profile = "<name>"` line as choosing the `[profiles.<name>]` table, which never sets the store. It refuses a line that names a profile no table defines.

As read in Codex 0.164.0, four settings limit which ChatGPT logins Codex keeps. Codex reads `forced_login_method` and `forced_chatgpt_workspace_id` from the same places as the store, and `allowed_login_methods` and `allowed_chatgpt_workspaces` from the requirements that pin the store. As the interactive `codex` starts, it signs out of a login the first two rule out and deletes it. Every Codex leaves unused a login that any of the four rules out. Pitboard puts no such login in use, and refuses with `login_restricted`. The `Codex login restrictions` line of `pitboard doctor` names each setting and the accounts it rules out.

Pitboard does not read three places Codex also reads:

- A trusted project's `.codex/config.toml`, which can move the login while Codex runs there.
- A profile's `<name>.config.toml`, read only with `--profile`, which `codex login` refuses.
- An enterprise's cloud configuration, which `codex login` does not load. Whether a running Codex follows its store is not known.

## Claude Desktop files

Pitboard reads these on macOS only. Claude's data folder is `~/Library/Application Support/Claude`. As read in Claude 2.7032.0, that `~` is your account's own home, whatever `HOME` says. Where `HOME` names another folder, Pitboard leaves Claude Desktop alone.

As measured in Claude 2.19675.0, eight items and three keys of `config.json` hold an account. Moving them moves it whole, both ways. As read in 2.42304.0, Claude clears more of the data folder when another account signs in, and Pitboard moves that with the account too. Pitboard moves them only while Claude is closed: the items by renaming, the keys by rewriting `config.json`. Any item may be missing.

| Path in the data folder | What Pitboard does with it |
| --- | --- |
| `Cookies` | Moves it with the account. A change reads the name, expiry and stored value of claude.ai's session cookies, and keeps an 8-byte fingerprint of the value. Pitboard decrypts nothing. |
| `Cookies-journal`, `Local Storage`, `Session Storage`, `WebStorage`, `File System` | Moves them with the account. |
| `IndexedDB/https_claude.ai_0.indexeddb.leveldb`, `IndexedDB/https_claude.ai_0.indexeddb.blob` | Moves them with the account. |
| `Service Worker`, `Platform Notifications`, `CdmStorage.db`, `declarative_performance_observer.db`, and the last two's `-journal` | Moves them with the account. Chromium keeps them for each site. |
| `Partitions`, `chrome-import-sites.json` | Moves them with the account: Claude's preview browsers, and the sites imported from Chrome into them. |
| `builtin-mcp-auth`, `custom3p-builtin-mcp.json`, `custom3p-builtin-mcp.json.journal` | Moves them with the account: the Microsoft 365 connector's sign-ins, where a policy sets it up. |
| `session-popouts.json`, `local-sessions.json` | Moves them with the account: the session windows Claude opens again, and the sessions an earlier build left for the next sign-in. |
| `config.json` | Claude's settings. A read takes the account they name, `lastKnownAccountUuid`, and whether both token caches are emptied. A change moves the keys `oauth:tokenCache`, `oauth:tokenCacheV2`, `lastKnownAccountUuid` and `custom3pMcpOAuth` with the account, and writes the other keys back as they were. |
| `reset-app-data`, `reset-app-data.given-up` | Read by each change. As read in 3.6556.2, Claude deletes what the data folder holds the next time it opens while `reset-app-data` waits there without `reset-app-data.given-up`. Pitboard then moves no login: see [Claude is waiting to reset its data](/troubleshooting/claude-desktop#claude-is-waiting-to-reset-its-data). |
| `config.json.journal` | A write of `config.json` that Claude has not finished. As read in 2.7032.0, Pitboard reads it as the settings where the hashes on its first line say it is valid. It ignores it where they say it is stale. Pitboard never deletes it. |
| Every other name | Stays in the data folder. As read in 3.6556.2, Claude keeps it when another account signs in too. Each change and `pitboard doctor` look for a `-journal`, `-wal`, `-shm` or `.journal` of an item above that no row names, another `IndexedDB/https_claude.ai_0.` store, and a `Network` folder, where Chromium can move the cookie store. Any of them stops a move: see [Account data in a form Pitboard has not read](/troubleshooting/claude-desktop#account-data-in-a-form-pitboard-has-not-read). |

As read in 2.7032.0, `claude-code-sessions` and `local-agent-mode-sessions` keep each account's sessions in a folder named for the account.

Beside the data folder, Pitboard looks for `Claude-3p/config.json`. As read in 3.6556.2, it is there once Claude has run as a third-party deployment, and Claude runs from `Claude-3p` until `deploymentMode` in `Claude-3p/claude_desktop_config.json` names `1p`. Pitboard reads that key, and moves no login while `Claude-3p/config.json` is there and the key does not name `1p`.

During a change, Pitboard holds an advisory lock on the data folder itself. It deletes nothing of Claude's there. For `pitboard doctor`, it reads Claude's build from `/Applications/Claude.app`.

Pitboard reads the list of processes to tell whether Claude is open:

| Program | Counts as Claude open |
| --- | --- |
| Inside an app whose bundle identifier is `com.anthropic.claudefordesktop`, whatever the app is named | Yes |
| Inside the data folder | Yes |
| Inside an app named `Claude.app` whose identifier Pitboard cannot read | Yes |
| `Contents/MacOS/Claude`, or inside `Contents/Frameworks/Claude Helper*.app`, in an app whose identifier Pitboard cannot read | Yes |
| A `chrome-native-host` that Chrome started for Claude's browser extension | No |

## Renewal schedule

`pitboard schedule install`, or turning on **Renew parked logins daily** in the app's **Settings** > **Advanced**, writes these. `pitboard schedule uninstall`, or turning it off, removes them. So does `pitboard uninstall` while Pitboard's directory is its default one. On Windows, [uninstalling the app](/install/remove#remove-pitboard-itself) removes the task where it runs the app's own `pitboard.exe`.

| Item | macOS | Windows | Linux |
| --- | --- | --- | --- |
| Where | `~/Library/LaunchAgents/com.datlechin.pitboard.renew.plist` | The task `\Pitboard\Renew <SID>` in Task Scheduler, `<SID>` being your account's security identifier | `pitboard-renew.service` and `pitboard-renew.timer` in `~/.config/systemd/user`, even with `XDG_CONFIG_HOME` set |
| Runs | `<program> renew` | `<program> renew --scheduled` | `<program> renew --scheduled` |
| When | `StartInterval` 86400 and `RunAtLoad` false: first a day after it is written | Each day at the time of day it was written, first a day after. Only while you are signed in, at least privilege, with a 10-minute limit, and as soon as it can after a missed start | `OnUnitActiveSec=86400`, `OnStartupSec=900` and `Persistent=true` |
| Environment | `EnvironmentVariables` | `schedule.env` in Pitboard's directory | One `Environment=` line each |

`<program>` is the `pitboard` that installed the job, by the path it was started with, such as Homebrew's link. From the app, it is the command line that came with it: `Pitboard.app/Contents/Helpers/pitboard` on macOS and `bin\pitboard.exe` in the app's folder on Windows.

The environment holds the proxy variables as they were set at install, and on macOS and Linux `PITBOARD_NO_ARGV`: see [`schedule`](/reference/maintenance-commands#schedule). Each file is private to you, since a proxy's address can hold a password. On Linux, systemd also hands the environment to programs that ask, as systemd.exec(5) says.

## Watch service

`pitboard watch install` writes these, and `pitboard watch uninstall` removes them. So does `pitboard uninstall` while Pitboard's directory is its default one. On Windows, [uninstalling the app](/install/remove#remove-pitboard-itself) removes the task where it runs the app's own `pitboard.exe`.

| Item | macOS | Windows | Linux |
| --- | --- | --- | --- |
| Where | `~/Library/LaunchAgents/com.datlechin.pitboard.watch.plist` | The task `\Pitboard\Watch <SID>` in Task Scheduler | `pitboard-watch.service` in `~/.config/systemd/user` |
| Runs | `<program> watch --scheduled --at <PERCENT>` | The same | The same |
| When | `RunAtLoad` true, so at install and at each login. `KeepAlive` with `SuccessfulExit` false and `Crashed` true, and `ThrottleInterval` 60: again a minute after it fails or crashes | At install, and at each sign-in to your Windows account. Only while you are signed in, at least privilege, with no time limit | At install, and as your user's systemd starts, through `WantedBy=default.target`. `Restart=on-failure` and `RestartSec=60`: again a minute after it fails or crashes |
| Environment | `EnvironmentVariables` | `watch.env` in Pitboard's directory | One `Environment=` line each |
| Lines it prints | `~/Library/Logs/Pitboard/watch.log`, removed with the service | Kept nowhere | Your user's journal |

`<program>` and the environment are as for the [renewal schedule](/reference/files#renewal-schedule).

    | `HKEY_CURRENT_USER\Software\Classes\pitboard` | The [Pitboard link](/reference/account-windows#pitboard-links) scheme |
    | The value `Pitboard` in `HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run` | **Start when you sign in to Windows**, while it is on: the app's path and `--sign-in` |

    The app keeps these in `Pitboard App` in the folder Windows names for your account's local app data, whatever `LOCALAPPDATA` or `PITBOARD_HOME` says:

    | File | Holds |
    | --- | --- |
    | `placement.json` | Where the Pitboard window was when it closed |
    | `updates.json` | The settings of WinSparkle, the app's updater, and when it last checked |
    | `windows.json` and `WebView2` | The account windows' records and data, as [Account windows](/reference/files#account-windows) lists |

    Removing Pitboard in **Settings** > **Apps** > **Installed apps** deletes the install folder, the shortcut, the link scheme, the `PATH` entry, the `Run` value and `%LOCALAPPDATA%\Pitboard App`.
  </Tab>
</Tabs>

Both apps keep these in `app.json` in Pitboard's directory, so they follow `PITBOARD_HOME`:

| Key | Holds |
| --- | --- |
| `second_account_declined` | The tools, `claude`, `codex` or `desktop`, whose second-account tip you dismissed with **Not Now** |
| `tips_declined` | The other setup tips you dismissed with **Not Now**: `open_at_login`, `at_limit` or `use_codex` |
| `has_been_seen` | Whether the app has opened its window at first launch |
| `at_limit` | The choice in **When a limit reaches**: `nothing`, `notify` or `switch`. While left out, `auto_switch` decides. |
| `auto_switch` | `true` while **Switch Automatically** is chosen. Left out otherwise. Without `at_limit`, `true` reads as **Switch Automatically** and anything else as **Notify Me**. |
| `auto_switch_at` | The share it notifies or switches at, a whole percentage. 95 while left out. A value outside 50 to 99 reads as the nearer end. |

## Account windows

[Account windows](/guides/account-windows) keep their data and records in your account's own folders, apart from Pitboard's directory, whatever the environment names. [How account windows keep their data](/concepts/account-windows) has the rules.

<Tabs>
  <Tab title="macOS">
    | Path | What it is |
    | --- | --- |
    | `~/Library/WebKit/com.usepitboard.Pitboard/WebsiteDataStore/<id>` | One account window's website data, sign-in included |
    | `~/Library/Application Support/com.usepitboard.Pitboard/windows.json` | The windows' records: the data folders the app made, by Pitboard directory, and the page each window was last on |
    | `~/Library/Containers/com.usepitboard.Pitboard.share` and `~/Library/Application Scripts/com.usepitboard.Pitboard.share` | Folders macOS makes for the sandboxed Share extension. Pitboard writes nothing there. |
    | `~/Downloads` | Where account windows save [downloads](/reference/account-windows#downloads) |

    These are under your account's own `~/Library`, whatever `HOME` says.
  </Tab>
  <Tab title="Windows">
    | Path | What it is |
    | --- | --- |
    | `%LOCALAPPDATA%\Pitboard App\WebView2\EBWebView\WV2Profile_<id>` | One account window's website data, sign-in included, as a WebView2 profile |
    | `%LOCALAPPDATA%\Pitboard App\windows.json` | The windows' records: the profiles the app made, by Pitboard directory, and the page each window was last on |
    | Your Downloads folder | Where account windows save [downloads](/reference/account-windows#downloads) |

    `%LOCALAPPDATA%` here is the folder Windows names for your account's local app data, whatever `LOCALAPPDATA` says.
  </Tab>
</Tabs>

`<id>` is a version 5 UUID of `claude:` or `codex:` and the account's id.
