The paths shown are defaults that [environment variables](/reference/files#environment-variables) can move.

## The Pitboard directory

Pitboard's directory is `~/.pitboard`, or the path in `PITBOARD_HOME`. The command line and the app share it.

Pitboard creates each directory at mode 0700 and each file at 0600, except those in `backups/`. An existing directory keeps its mode.

Pitboard refuses a directory that a sync client copies to other machines, because parked logins belong to one machine. It refuses one whose path contains `Dropbox`, `Google Drive`, `OneDrive`, `com~apple~CloudDocs` or `Sync`, written so. It also refuses one inside `~/Library/CloudStorage` or `~/Library/Mobile Documents`, and one inside a folder with one of these names, in any case and wherever it is in the path, your home's own folders included: `OneDrive`, `OneDrive - <organisation>`, `OneDrive-<kind>`, `Dropbox`, `Dropbox (<team>)`, `Google Drive`, `GoogleDrive-<account>`, `com~apple~CloudDocs` or `Sync`.

| File | Holds | Written by |
| --- | --- | --- |
| `state.json` | The enrolled accounts: label, tool, email address, account identifiers, a Codex account's ChatGPT plan such as `plus` or `team`, each parked login's name and expiry, and when a sign-in outside Pitboard replaced an account's only login. For each tool, and each `CLAUDE_CONFIG_DIR` or `CODEX_HOME` it was read under, whose login it has stored, as Anthropic or the login itself last said, with a fingerprint of that login, when that was said, and the account the tool's own record named then. | Every change Pitboard makes, renewals, and a read that finds whose login a tool has stored changed |
| `state.lock` | The lock that lets one change or renewal run at a time | Every change Pitboard makes, renewals, and a read that records whose login a tool has stored |
| `journal.json` | The record of a switch while it runs. An interrupted switch leaves it behind, and the next change Pitboard makes finishes or undoes it; see [Interrupted switches](/concepts/switching#interrupted-switches). | A switch |
| `autoswitch.json` | What [automatic switching](/guides/automatic-switching) has tried for each limit of a Claude Code account that reached the share it switches at. Each entry holds when the limit resets, how many tries count against it, how many in a row failed for a reason that may pass, such as Anthropic being out of reach, when the last try began, whether one switched, and the accounts passed over. It holds account ids, limit names, times and counts, and nothing secret. An entry is dropped at the first write after its limit resets or, where that time is unknown, 7 days after its last try. | An automatic switch, from the app or `pitboard watch`, under `state.lock` |
| `pending` | Names of parked logins about to be written, one per line. If a run is killed midway, the next change Pitboard makes finds each login by its name here. Absent when there are none. | Switches, sign-ins and renewals |
| `signin.lock` | The lock that allows one sign-in at a time | A sign-in |
| `signin/` | The config directory a tool is given during a sign-in, so the login in use is left alone. Removed when the sign-in ends, or by the next sign-in if Pitboard was stopped during one. | A sign-in |
| `vault/` | Linux only: parked logins, one file each | Switches, sign-ins and renewals |
| `usage.json` | The newest usage reading for each account | Reading usage, and the status line |
| `usage.lock` | The lock around `usage.json` and `sessions.json` | Reading usage, and the status line |
| `asking.json` | When Pitboard last asked Anthropic or OpenAI for each account's usage, and how long to wait before asking again | Reading usage |
| `sessions.json` | The usage each Claude Code session last gave `pitboard statusline`, and the account in use then. A session not seen for 7 days is dropped. | The status line |
| `backups/` | Copies of Claude Code's config from before each switch rewrote it. Each is named after the time it was made, in seconds since 1 January 1970, such as `claude.json.1790000000`. The 10 newest are kept. They hold no login, but do hold your email address, your Anthropic account and organisation identifiers, and the path of each project Claude Code has opened. Each keeps the mode of Claude Code's file. | A Claude Code switch |
| `audit.log` | One tab-separated line per change or renewal: the time, `cli` or `app` for where it was made, the verb such as `use`, the subject and the outcome. It holds no email address, and holds an account id only in a `reclaim` line with the outcome `discarded`, whose subject is a parked login's name. [`pitboard log`](/reference/maintenance-commands#log) prints it. | Every change Pitboard makes, and renewals |
| `audit.log.1` | The previous `audit.log`, moved aside once it passed 256 KiB | Every change Pitboard makes, and renewals |
| `app.json` | The app's own preferences: the tools for which you clicked **Not Now** when the **Accounts** pane suggested a second account, whether the app has opened its window at first launch, and the **Before an account runs out** settings. `auto_switch` is `true` while **Switch Claude Code automatically** is on, and left out while it is off. `auto_switch_at` is the share it switches at, as a whole percentage, and 95 while it is left out. | The app |
| `told.json` | Each limit the app has notified you ran out, by tool, account and limit, with the time it resets, so the app notifies each run-out once | The app |

Only files in `vault/` and `signin/` can hold a login. To delete the directory, see [Remove Pitboard](/install/remove#delete-parked-logins-and-pitboard%E2%80%99s-files).

## Parked logins

On macOS, each parked login is an item in your default keychain, named `pitboard-park-<account id>-<time>`. Its keychain account is the one Claude Code's item uses, usually your user name from `USER`.

`<account id>` is the id Pitboard keeps for the account. For Claude Code, it is the Anthropic account UUID and the organisation UUID joined with `_`, and an account enrolled by Pitboard 0.8.0 or earlier keeps its account UUID alone. For OpenAI's Codex CLI, it is built from the account's ChatGPT ids. `<time>` is when the login was parked or last renewed, in milliseconds since 1 January 1970.

On Linux, each parked login is a file in `~/.pitboard/vault/`, named `pitboard-park-<account id>-<time>.json`.

For why parked logins are kept there, see [Security and privacy](/security#where-parked-logins-are-kept).

## Claude Code and Codex files

| Path | What Pitboard does with it |
| --- | --- |
| `~/.claude.json` | Reads which account it names, which can be another than the one whose login is stored. Pitboard takes a change of it since Anthropic last named the login stored as a sign that something signed in, never as the account in use. After a Claude Code switch, copies it to `backups/` and writes the incoming account into it. A `~/.claude/.config.json`, where one exists, is used instead. |
| Keychain item `Claude Code-credentials` | macOS: the Claude Code login in use. A switch reads and replaces it. With `CLAUDE_CONFIG_DIR` set, the name ends in `-` and 8 hex characters from a hash of the directory's path. |
| `~/.claude/.credentials.json` | Linux: the Claude Code login in use. macOS: Claude Code's fallback when a keychain write fails for good, which Pitboard reads after the keychain item. A locked keychain whose item Claude Code has seen does not count, from Claude Code 2.1.281. Where the keychain holds a login too, Pitboard never writes the file. While it is there, whatever it holds, `doctor`, each change and each read but `status --offline` warn. See [Claude Code over SSH uses another account](/troubleshooting#claude-code-over-ssh-uses-another-account). |
| `~/.claude/.storage-write.lock` | The lock Claude Code takes around each write of its login. Pitboard takes it during a switch. |
| `~/.claude/settings.json` | Read for `apiKeyHelper`, and for an `env` block that sets `CLAUDE_CODE_CUSTOM_OAUTH_URL` or a variable that overrides Claude Code's login, listed in [Environment variables](/reference/files#environment-variables). Managed settings are read too: `managed-settings.json` and `managed-settings.d/*.json` in `/Library/Application Support/ClaudeCode` on macOS or `/etc/claude-code` on Linux. A project's settings are not read. |
| `~/.codex/auth.json` | The Codex login in use. A switch reads and replaces it. |
| `~/.codex/config.toml` | Read for `cli_auth_credentials_store`, and for `secret_auth_storage` in `[features]`. For the values Pitboard refuses, see [Use Pitboard with Codex](/guides/codex#before-you-enrol-a-codex-account). |
| `/etc/codex/config.toml`, `/etc/codex/managed_config.toml` and `/etc/codex/requirements.toml` | Read for the same two settings, never written. On macOS, so are the managed preferences `config_toml_base64` and `requirements_toml_base64` of `com.openai.codex`, which a configuration profile sets. For the order Codex reads them in, see [Where Codex reads the setting](/guides/codex#where-codex-reads-the-setting). A project's own `.codex/config.toml`, a profile's `<name>.config.toml` and configuration an enterprise manages are not read. |

For how a switch changes these files, see [How switching works](/concepts/switching#what-a-switch-does).

## Renewal schedule

`pitboard schedule install`, or turning on **Renew parked logins daily** in **Settings** > **General**, writes these files. `pitboard schedule uninstall`, or turning it off, removes them. So does `pitboard uninstall` when Pitboard's directory is `~/.pitboard`.

| Item | macOS | Linux |
| --- | --- | --- |
| Files | `~/Library/LaunchAgents/com.datlechin.pitboard.renew.plist` | `~/.config/systemd/user/pitboard-renew.service` and `~/.config/systemd/user/pitboard-renew.timer`, even when `XDG_CONFIG_HOME` is set |
| Name | launchd label `com.datlechin.pitboard.renew` | unit `pitboard-renew.timer` |
| Program | The `pitboard` that installed it, by the path it was started with, such as Homebrew's link, so an upgrade does not break it. From the app: `Pitboard.app/Contents/Helpers/pitboard` | The `pitboard` that installed it, by the path it was started with, such as Homebrew's link, so an upgrade does not break it |
| Runs | `<program> renew` | `<program> renew --scheduled`, where a timer installed by an earlier Pitboard runs `<program> renew` |
| When | Once a day, first a day after it is written: `StartInterval` 86400, `RunAtLoad` false | Once a day: `OnUnitActiveSec=86400`, `OnStartupSec=900` |
| Environment | `EnvironmentVariables`: `PITBOARD_NO_ARGV` and the [proxy variables](#environment-variables), as they were set where it was installed | One `Environment=` line in the service for each of the same variables |
| Access | Only you can read or change it: mode 600, since a proxy's address can hold a password | Only you can read or change either file: mode 600 |

## The app

The app is `Pitboard.app`, with the bundle identifier `com.usepitboard.Pitboard`.

| Path inside `Pitboard.app` | What it is |
| --- | --- |
| `Contents/Helpers/pitboard` | The command line |
| `Contents/Resources/man/pitboard.1` | The man page |
| `Contents/Resources/completions/pitboard.bash`, `pitboard.zsh` and `pitboard.fish` | Shell completions |
| `Contents/PlugIns/PitboardShare.appex` | The [Share extension](/reference/app#share-extension), **Pitboard** in a browser's Share menu |

The app stores these keys in `~/Library/Preferences/com.usepitboard.Pitboard.plist`:

| Key | Holds |
| --- | --- |
| `menuBarShows` | **Menu bar shows**: `nameAndUsage`, `usage` or `icon` |
| `settingsTab` | The Settings tab shown last: `general`, `commandLine` or `updates` |
| Keys of Sparkle, the app's updater | Its update settings and when it last checked |

macOS keeps **Open Pitboard at login** as a login item, outside this file.

Earlier versions of the app kept `hasBeenSeen` and `secondAccountDeclined` in this file, and before them `hideSecondAccountNudge`. The app takes what they held into `app.json` the first time it opens a Pitboard directory without one, and removes them from this file once `app.json` is there.

Earlier versions also kept the [account windows'](#account-windows) records here, as `webStores` and `windowPages`. The app takes what they held into `windows.json` the first time it opens without one, and removes them from this file once `windows.json` is there.

The app's files can also be in `~/Library/Application Support`, `~/Library/Caches`, `~/Library/HTTPStorages` and `~/Library/Saved Application State`, named after `com.usepitboard.Pitboard`. In `Saved Application State`, macOS keeps the windows that were open, to restore them. To remove these files, see [Remove Pitboard](/install/remove#remove-pitboard-itself).

### Account windows

The [account windows](/reference/app#account-windows) and the Share extension keep their files in these places:

| Path | What it is |
| --- | --- |
| `~/Library/WebKit/com.usepitboard.Pitboard/WebsiteDataStore/<id>` | One account window's website data: the site's cookies, the sign-in among them, its storage and its caches. WebKit writes it, and a sign-in window shares its account's folder. Pitboard never reads, copies or changes what is in it. |
| `~/Library/Application Support/com.usepitboard.Pitboard/windows.json` | The windows' records: the data folders the app made, listed under the path of the Pitboard directory it made them for, and the page each window was last on. The app deletes only these folders. Only a site's own pages are kept, never its sign-in pages. Removing a window's data or forgetting its account takes its page away. Readable only by you. |
| `~/Library/Containers/com.usepitboard.Pitboard.share` and `~/Library/Application Scripts/com.usepitboard.Pitboard.share` | Folders macOS makes for the sandboxed Share extension. Pitboard writes nothing there. |
| `~/Downloads` | Where account windows save downloads. A name already taken gets a number, as in `report 2.pdf`. |

`<id>` is a version 5 UUID made from `claude:` or `codex:` and the account's id, so the folder's name does not show the id. A renamed account keeps its folder, and with it the window's sign-in.

WebKit keeps the windows' folders under your own `~/Library`, whatever `HOME` says. So the app records in `windows.json`, beside them, the folders it made for its Pitboard directory, `~/.pitboard` or `PITBOARD_HOME`. It deletes only those, and a copy run with another `HOME` or `PITBOARD_HOME` leaves them alone. If `windows.json` is there but the app cannot read it, or cannot read records in it, the app deletes no folder. It never writes over that file. Each window then opens at its site's home with the sign-in note at each launch, and keeps its data.

The app deletes a folder once a successful read of the accounts no longer lists its account. That happens after you forget the account, in the app or with `pitboard forget`. A folder WebKit still holds is tried a few more times, then again at the next read.

A folder that another Pitboard directory also recorded is kept, and only the record of the directory the app reads is removed. Both record it when the same account's window has opened from each. If that other directory no longer exists, the app deletes the folder.

**Remove Website Data** in the **File** menu removes the data in a folder and keeps the folder.

## Environment variables

Opened from Finder, the app does not see your shell's variables, so the defaults apply. Daily renewal runs with the scheduler's environment, not your shell's.

Pitboard refuses an empty `HOME`, `PITBOARD_HOME` or `CLAUDE_CONFIG_DIR`, and a path that does not start at the root in any of them or in `CLAUDE_SECURESTORAGE_CONFIG_DIR` or `CODEX_HOME`, with the error `home_not_absolute`. The folder such a path names depends on where each program runs.

| Variable | Read by | Effect |
| --- | --- | --- |
| `HOME` | Both | Your home directory, the `~` in every path here. |
| `PITBOARD_HOME` | Both | Pitboard's directory, in place of `~/.pitboard`. Daily renewal always renews `~/.pitboard`, even when its job is given this variable, and Pitboard refuses to turn it on while this names another directory. |
| `PITBOARD_NO_ARGV` | Both | On macOS, when it is `1`, Pitboard refuses to write a large login on `security`'s argument line, and does not renew a parked login it could not write back. A renewal schedule installed while it is set keeps it. See [Large logins on macOS](/security#large-logins-on-macos). |
| `PITBOARD_API_BASE` | Command line | For Pitboard's tests. Sends the requests meant for Anthropic and OpenAI to this URL, if it is an `http` URL whose host is a loopback IP address, such as `http://127.0.0.1:8080`. |
| `CLAUDE_CONFIG_DIR` | Both | Claude Code's config directory, in place of `~/.claude`. The config file becomes `$CLAUDE_CONFIG_DIR/.claude.json`, and the keychain item's name gets a suffix. Set but empty, Claude Code keeps its config directory in whatever folder it runs in, so Pitboard refuses it. |
| `CLAUDE_SECURESTORAGE_CONFIG_DIR` | Both | The directory that picks Claude Code's keychain item, `.credentials.json` and lock, in place of the config directory. Set but empty, it picks `~/.claude` and `Claude Code-credentials`. |
| `USER` | Both | macOS: the keychain account of Claude Code's item and of parked logins. Unset or empty, your login name is used. A name with characters other than letters, digits, `.`, `_` and `-` becomes `claude-code-user`. |
| `CLAUDE_CODE_CUSTOM_OAUTH_URL` | Command line | Not empty: Pitboard refuses every change to a Claude Code account, `abandon` of a Claude Code switch, `repair` and `uninstall`, with the error `custom_oauth_endpoint`. Claude Code then keeps its login under a name Pitboard does not read. Automatic switching holds back and says why. The command line and the app also read it from an `env` block in Claude Code's settings. |
| `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY`, `CLAUDE_CODE_USE_GATEWAY`, `CLAUDE_CODE_USE_ANTHROPIC_AWS`, `CLAUDE_CODE_USE_ANTHROPIC_GOOGLE_CLOUD` | Command line | Any of these not empty: Claude Code uses something other than the login Pitboard switches. Changes to Claude Code accounts warn with `auth_overridden`, and `pitboard doctor` warns. Automatic switching holds back and says why. The command line and the app also read these, and `apiKeyHelper`, from Claude Code's settings. |
| `CODEX_HOME` | Both | Codex's directory, in place of `~/.codex`. Empty counts as unset. |
| `SUDO_UID` | Both | Not empty, as `sudo` sets it: Pitboard runs with `sudo`, so it refuses every command that changes something, with the error `elevated`. See [Pitboard changes nothing as root](/troubleshooting#pitboard-changes-nothing-as-root). |
| `PATH` | Command line | Where the command line looks for `claude` and `codex`, which it runs to sign in. Only absolute directories are searched. |
| `NO_COLOR` | Command line | Not empty: no colour in any output. `pitboard statusline` also drops its colour when `NO_COLOR` is set but empty. |
| `ALL_PROXY`, `HTTPS_PROXY`, `HTTP_PROXY` | Both | The proxy Pitboard's requests to Anthropic and OpenAI go through. Pitboard reads `ALL_PROXY`, `all_proxy`, `HTTPS_PROXY`, `https_proxy`, `HTTP_PROXY`, then `http_proxy`, and takes the first that holds a proxy's address. An address with no scheme is `http://`. Pitboard goes through `http://` and `https://` proxies. It does not go through SOCKS proxies, `socks4://`, `socks4a://`, `socks5://`, `socks5h://` and `socks://`, and sends nothing around one: while the variable Pitboard takes names one, each request to a host `NO_PROXY` does not name fails before anything is sent, saying which variable named it. A renewal schedule installed while these are set keeps them, as written, even after you change them. |
| `NO_PROXY` | Both | The hosts Pitboard reaches without the proxy, separated by commas and compared without regard to case. Pitboard does not look up the proxy's own name for them, so they are reached where that name is not found, such as off a company network. While a SOCKS proxy is named, Pitboard still reaches these hosts directly, and does not follow a redirect from one. `*` is every host. An entry starting with `*` is every host ending with what follows the `*`, and one starting with `.` every host ending with the whole entry. So `*.example.com` and `.example.com` are the hosts under `example.com`, and `*example.com` is also `badexample.com`. An entry ending with `*` is every host starting with what comes before it, and one ending with `.` every host starting with the whole entry, so `10.` is every address starting `10.`. Any other entry is that host alone. A space is part of the entry. When `NO_PROXY` is unset, Pitboard reads `no_proxy`. A renewal schedule installed while either is set keeps it. |
| `PITBOARD_CLAUDE`, `PITBOARD_CODEX` | App | The path of the `claude` or `codex` program the app runs to sign in, in place of the one it finds. |
