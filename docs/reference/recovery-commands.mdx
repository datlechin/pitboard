None of these commands takes an argument. [JSON output](/reference/json-output#data-by-command) lists what each prints with `--json`.

## `stow`

`pitboard stow` puts away Claude Code's `.credentials.json` where it sits behind the keychain on macOS, or behind Credential Manager on Windows. The [`fallback_login`](/reference/errors#warning-codes) warning names that file. While it is there, open Claude Code sessions follow a switch only at their next renewal, as [Open sessions](/concepts/open-sessions) explains. [Claude Code over SSH uses another account](/troubleshooting#claude-code-over-ssh-uses-another-account) says how the file gets there.

| Option | Description |
| --- | --- |
| `-y, --yes` | Do not ask first; needed without a terminal or with `--json` |

At a terminal, `stow` says what the file holds and asks first, as [Questions before deleting](/reference/commands#questions-before-deleting) describes. Anywhere else, such as in a script or with `--json`, it needs `--yes`. Without it, `stow` refuses with `confirmation_needed` and deletes nothing.

<Warning>
  Deleting the file signs out a Claude Code session that signed in with it, as one over SSH does where it cannot read the keychain or Credential Manager.
</Warning>

`stow` identifies the login in the file by its refresh token where Pitboard knows that token. Otherwise it asks Anthropic, with the login's own access token.

It never sends an expired access token. It renews such a login first and writes it back to the file before anything else. That write keeps the file's other keys. If `stow` is killed before the write, or the write fails, the next change writes the renewed login to the file, and `stow` then says the file changed. Until then, `stow` changes nothing and says why.

Where the outcome turns on whose login Claude Code has stored, `stow` identifies that login too. If its access token has expired, the question before `stow` uses the account Pitboard last recorded, and `stow` itself renews the login as [a switch does](/concepts/identity).

It then keeps the login where it is not kept already, and deletes the file:

| The file holds | What `stow` does | `login` |
| --- | --- | --- |
| No Claude Code login, such as `{}`, an empty file or one that is not JSON | Deletes the file | `no_login` |
| The login Claude Code has stored | Deletes the file | `stored` |
| The login parked for an account | Deletes the file | `already_parked` |
| Another login of the account in use | Deletes the file and that second sign-in. The keychain or Credential Manager keeps the account's own login | `second_sign_in` |
| A login of an enrolled account with no parked login it can switch to | Parks the login for that account in place of any other, then deletes the file | `parked` |
| Another login of an account with a parked login it can switch to | Keeps that parked login and deletes the file | `park_kept` |
| A login Anthropic no longer accepts, or one with no refresh token whose access token has expired | Deletes the file | `login_refused` |

`login` is the `--json` field, and the outcome [`log`](/reference/maintenance-commands#log) records.

A parked login that an earlier, stopped `stow` copied from the file does not count as one the account can switch to. A session using the file may have renewed the login since, spending the copy.

From its last reading of the file until the file is gone, `stow` holds the locks Claude Code takes before it renews a login. [Claude Code files](/reference/files#claude-code-files) names them.

On macOS, parking a login too large for the keychain's standard input warns `written_on_the_command_line`. See [Large logins on macOS](/security#large-logins-on-macos).

`stow` stops with a code from [Claude Code and Codex files](/reference/errors#claude-code-and-codex-files), [Credential stores and locks](/reference/errors#credential-stores-and-locks) or [Command output](/reference/errors#command-output), such as `left_login_not_enrolled`. None of them deletes the file. Once `stow` begins putting the file away, an error ends with how far it got:

- `Pitboard changed nothing.`
- `Pitboard deleted nothing, having renewed the login in the file and written it back there.`
- ``Pitboard deleted nothing, having parked the login in the file for `work`.``
- `Pitboard deleted nothing. It renewed the login the file held and keeps the renewed login until the next change writes it back there.`
- `Pitboard deleted nothing. It renewed the login the file held and could not write the renewed login back there, so that login no longer works.` A sign-in replaced the file's login meanwhile, or neither the file nor the store in front of it could take the renewed login.
- `Pitboard deleted nothing. It renewed the login Claude Code has stored and keeps the renewed login until the next change saves it there.`

Where `stow` renews the login Claude Code has stored and can keep the answer nowhere, the error ends with ``Run `claude`, sign in, then try again.`` instead.

With nothing behind the keychain or Credential Manager, `stow` changes nothing. It prints `Nothing is left behind the store Claude Code keeps its login in, so there is nothing to put away.` On Linux it always prints that, and on Windows while `.credentials.json` is Claude Code's store: the file is where Claude Code keeps its login.

```sh
pitboard stow --yes
```

```text
Parked the login /Users/you/.claude/.credentials.json held for `work`, then deleted the file.
It also held 1 other key, `mcpOAuth`, which went with the file: Pitboard does not move it, and Claude Code's document in the keychain keeps its own.
Once the file is gone, Claude Code sessions already running follow a switch within 33 seconds again, and one that signed in with its login, such as one over SSH, is signed out.
```

On Windows, the output names Credential Manager where this one names the keychain.

In the app, **Clean Up** on the notice **A leftover sign-in file** does the same, as [Notices](/reference/mac-app#notices) lists. On Windows, the button is **Clean up**.

## `abandon`

`pitboard abandon` ends what an interrupted change left waiting, and keeps every login.

| What waits | What `abandon` does |
| --- | --- |
| An [interrupted switch](/concepts/switching#interrupted-switches) of Claude Code or OpenAI's Codex CLI | Deletes `journal.json` in Pitboard's directory, the switch's record, and writes no login. Each tool keeps the login it has, and both accounts of the switch keep their parked logins. |
| An interrupted Claude Desktop move that Pitboard can settle | Settles it, and warns `interrupted_move_undone` or `interrupted_move_finished`. |
| An interrupted Claude Desktop move that Pitboard cannot settle | Gives it up and keeps every folder. |

Giving up a Codex switch drops a parked login that copies the login in use. [Why Codex logins are moved, not copied](/concepts/switching#why-codex-logins-are-moved-not-copied) says why.

Giving up a Claude Desktop move moves nothing in or out of Claude's data folder. Items of the account left there stay, and a later change sets them aside.

A Claude Desktop move that `abandon` cannot give up still waits, and `abandon` refuses with the reason, such as `app_open`. Where giving it up would leave items beside another login in the data folder, the reason is `move_mixed`. Where `abandon` gave up a Claude Code or Codex switch first, it warns `move_not_given_up` with the reason instead.

While `CLAUDE_CODE_CUSTOM_OAUTH_URL` is set and a Claude Code switch is interrupted, `abandon` refuses with `custom_oauth_endpoint`, exit status 3, and gives up nothing. With no Claude Code switch interrupted, the variable does not stop it.

After an interrupted switch from `work` to `personal`:

```sh
pitboard abandon
```

```text
Gave up on the interrupted switch from work to personal. 2 login(s) kept; nothing was deleted. Run `pitboard` to see who is signed in.
```

| Output | When |
| --- | --- |
| ``Pitboard gave up the move of `desktop/work`'s login and kept every folder: 1 parked, 1 set aside. Run `pitboard enroll desktop/<label>` for the account Claude shows, or `pitboard use desktop/<label>` where Claude is signed out.`` | It gave up a Claude Desktop move. The line follows that of a switch given up. |
| `There is no interrupted switch to give up on.` | Nothing waited. It changes nothing. |

The Claude Desktop line changes in two cases:

| Case | The line |
| --- | --- |
| The move was in another data folder, which `abandon` gives up without reading | Adds `The move was in /Users/dana/Library/Application Support/Claude, which Pitboard did not read.` after its first sentence |
| Items of the account stay in the data folder | Names them, as in `` `Session Storage` and `WebStorage` stay in Claude's folder. ``, and asks you to open Claude once and quit it with Command-Q before you run either command |

[An interrupted switch cannot be finished](/troubleshooting/recovery#an-interrupted-switch-cannot-be-finished) and [A Claude Desktop move was interrupted](/troubleshooting/recovery#a-claude-desktop-move-was-interrupted) say when to run it.

## `repair`

`pitboard repair` finds parked logins that Pitboard's account list does not name.

| Parked logins | Where `repair` looks |
| --- | --- |
| Claude Code and Codex, on macOS | Keychain items whose names start with `pitboard-park-`. Listing reads only names, so macOS does not ask for permission. |
| Claude Code and Codex, on Linux | Files in `~/.pitboard/vault/` |
| Claude Code and Codex, on Windows | Files in `vault` in `%USERPROFILE%\AppData\Local\Pitboard` |
| Claude Desktop, on macOS | Folders in `~/.pitboard/parks/` |

It adds the names in `pending` in Pitboard's directory, then reads each one the account list does not name.

Pitboard writes a parked login's name to `pending` before creating it. Every switch, enrolment, `forget`, `rename`, `stow` and `uninstall` resolves the names on that list as it starts, without listing the keychain. A parked login is missing from both only after Pitboard's directory is lost or restored from a backup. That is when `repair` is needed.

| What waits | What `repair` does first |
| --- | --- |
| An interrupted switch | Finishes or undoes it, as `use` does. Stops if it cannot. |
| An interrupted Claude Desktop move | Settles it, as a change does. Where it cannot, such as while Claude is open, it warns `move_not_settled` with why, and repairs the rest. |

With no move waiting, `repair` reads nothing of Claude.

It gives a parked login back to the enrolled account whose id is in its name when:

| Parked login | Given back when |
| --- | --- |
| Claude Code or Codex | Its refresh token has not expired. The account holds no parked login, or `pending` names this one and the account holds an older one. It is not a copy of the Codex login in use. |
| Claude Desktop | The folder's manifest, keys and cookie store agree. The account holds no parked login and is not in use. |

A Claude Desktop account whose parked login's folder is gone, as after `state.json` is restored from a backup, counts as holding none. `repair` gives back a folder set aside earlier on the same terms. It sets aside the folders no account can take, and deletes none that holds an item.

| Output | When |
| --- | --- |
| `Gave personal back a parked login that nothing named.` | It gave a login back. One line per login |
| `Deleted 1 parked login(s) Pitboard wrote down here and nothing recorded.` | No account could take logins that `pending` names |
| `1 parked login(s) here belong to no account Pitboard knows and were not written down by this one. Left alone: the keychain is shared by the whole machine, and they may be another Pitboard's.` | On macOS, no account could take logins that `pending` does not name |
| `1 parked login(s) here belong to no account Pitboard knows and were not written down by this one. Left alone: Pitboard deletes only a parked login it wrote down.` | On Linux and Windows, no account could take logins that `pending` does not name |
| `1 could not be read this time and were left alone. Unlock the keychain and run this again.` | On macOS, it could not read logins, as while the keychain is locked |
| `1 could not be read this time and were left alone. Run this again from a desktop session.` | On Windows, it could not open logins, as in a sign-in over SSH with a key |
| `1 could not be read this time and were left alone.` | On Linux, it could not read logins |
| ``Set aside 1 folder(s) in /Users/you/.pitboard/parks that hold what no account here can take. Nothing was deleted; `pitboard doctor` lists them.`` | No account could take folders |
| `Every parked login here is accounted for.` | It found nothing to do |

While `CLAUDE_CODE_CUSTOM_OAUTH_URL` is set, `repair` refuses with `custom_oauth_endpoint`, exit status 3.

[Pitboard lost track of parked logins](/troubleshooting/recovery#pitboard-lost-track-of-parked-logins) says when to run it.

## `adopt`

`pitboard adopt` takes over a Pitboard directory another computer wrote. Until you run it, commands that read the account list refuse that directory with `state_wrong_machine`.

It keeps every account with its label, email and remembered usage. Each parked login goes one of three ways:

| Parked login | What `adopt` does |
| --- | --- |
| Claude Code or Codex | Drops it, without asking Anthropic or OpenAI whether it still works |
| Claude Desktop, parked on another Mac | Sets it aside. Claude cannot read it here, where its key differs. `pitboard forget` of the account deletes it. |
| Claude Desktop, parked on this Mac | Keeps it for its account |

Asking whether a login works means renewing it, and nobody has measured whether that ends the other computer's copy. [What Pitboard will not do](/concepts/limits#rules) says why a parked login never moves between computers.

| What waits | What `adopt` does |
| --- | --- |
| An interrupted switch | Leaves it for the next change to finish or undo |
| A Claude Desktop move or sign-in | Drops its record, and sets aside each folder it names that no account holds |

```sh
pitboard adopt
```

```text
Took over this directory: 2 account(s) kept.
1 parked login(s) dropped, because a login belongs to the computer that signed in.
Sign in to each again:
  pitboard enroll personal --sign-in
```

Where it set Claude Desktop logins aside, a line before `Sign in to each again:` names them:

```text
Pitboard set aside the parked Claude Desktop logins of `desktop/work` and `desktop/home`. They were parked on another Mac, and Claude cannot read them here where its key differs. `pitboard forget` of an account deletes its own.
```

Each of those accounts then gets its own `pitboard enroll desktop/<label> --sign-in` line, after the lines of the logins dropped. The count of logins dropped leaves them out.

If the directory is already this computer's, `adopt` prints `This Pitboard directory was already written on this computer.` and changes nothing.

[The Pitboard directory came from another computer](/troubleshooting/recovery#the-pitboard-directory-came-from-another-computer) says when to run it.
