None of these commands takes an argument. [JSON output](/reference/json-output#data-by-command) lists what each prints with `--json`.

## `stow`

On macOS, `pitboard stow` puts away `~/.claude/.credentials.json` where it sits behind the keychain. The [`fallback_login`](/reference/errors#warning-codes) warning names that file. While it is there, open Claude Code sessions follow a switch only at their next renewal, as [Open sessions](/concepts/switching#open-sessions) explains. [Claude Code over SSH uses another account](/troubleshooting#claude-code-over-ssh-uses-another-account) says how the file gets there.

| Option | Description |
| --- | --- |
| `-y, --yes` | Do not ask first; needed without a terminal or with `--json` |

At a terminal, `stow` says what the file holds and asks first, as [Questions before deleting](/reference/commands#questions-before-deleting) describes. Anywhere else, such as in a script or with `--json`, it needs `--yes`. Without it, `stow` refuses with `confirmation_needed` and deletes nothing.

<Warning>
  Deleting the file signs out a Claude Code session that signed in with it, as one over SSH does while the keychain is locked.
</Warning>

`stow` identifies the login in the file by its refresh token where Pitboard knows that token. Otherwise it asks Anthropic, with the login's own access token.

It never sends an expired access token. It renews such a login first and writes it back to the file before anything else. That write keeps the file's other keys. If `stow` is killed before the write, or the write fails, the next change writes the renewed login to the file, and `stow` then says the file changed. Until then, `stow` changes nothing and says why.

Where the outcome turns on whose login Claude Code has stored, `stow` identifies that login too. If its access token has expired, the question before `stow` uses the account Pitboard last recorded, and `stow` itself renews the login as [a switch does](/concepts/switching#how-pitboard-knows-whose-login-it-is).

It then keeps the login where it is not kept already, and deletes the file:

| The file holds | What `stow` does | `login` |
| --- | --- | --- |
| No Claude Code login, such as `{}`, an empty file or one that is not JSON | Deletes the file | `no_login` |
| The login Claude Code has stored | Deletes the file | `stored` |
| The login parked for an account | Deletes the file | `already_parked` |
| Another login of the account in use | Deletes the file and that second sign-in. The keychain keeps the account's own login | `second_sign_in` |
| A login of an enrolled account with no parked login it can switch to | Parks the login for that account in place of any other, then deletes the file | `parked` |
| Another login of an account with a parked login it can switch to | Keeps that parked login and deletes the file | `park_kept` |
| A login Anthropic no longer accepts, or one with no refresh token whose access token has expired | Deletes the file | `login_refused` |

`login` is the `--json` field, and the outcome [`log`](/reference/maintenance-commands#log) records.

A parked login that an earlier, stopped `stow` copied from the file does not count as one the account can switch to. A session using the file may have renewed the login since, spending the copy.

From its last reading of the file until the file is gone, `stow` holds the locks Claude Code takes before it renews a login. [Claude Code files](/reference/files#claude-code-files) names them.

Parking a login too large for the keychain's standard input warns `written_on_the_command_line`. See [Large logins on macOS](/security#large-logins-on-macos).

These errors stop it:

| Error | When |
| --- | --- |
| `left_login_not_enrolled` | The login is of an account not enrolled here. The message names it and says how to enrol it |
| `confirmation_needed` | `stow` cannot ask, and `--yes` is not given. Exit status 2 |
| `left_login_changed` | The file changed or went after `stow` read it |
| `stored_login_changed` | The file was going because of the login Claude Code has stored, and a sign-in replaced that login meanwhile |
| `left_login_unidentified` | Pitboard could not identify or renew the login with Anthropic. A [cause code](/reference/errors#cause-codes) says why |
| `credential_store_locked` | The keychain is locked |
| `credential_store_unreadable` | Pitboard cannot read the file or the keychain |
| `custom_oauth_endpoint` | `CLAUDE_CODE_CUSTOM_OAUTH_URL` is set, as [Environment variables](/reference/files#environment-variables) describes. Exit status 3 |

None of them deletes the file. Once `stow` begins putting the file away, an error ends with how far it got:

- `Pitboard changed nothing.`
- `Pitboard deleted nothing, having renewed the login in the file and written it back there.`
- ``Pitboard deleted nothing, having parked the login in the file for `work`.``
- `Pitboard deleted nothing. It renewed the login the file held and keeps the renewed login until the next change writes it back there.`
- `Pitboard deleted nothing. It renewed the login the file held and could not write the renewed login back there, so that login no longer works.` A sign-in replaced the file's login meanwhile, or neither the file nor the keychain could take the renewed login.
- `Pitboard deleted nothing. It renewed the login Claude Code has stored and keeps the renewed login until the next change saves it there.`

Where `stow` renews the login Claude Code has stored and can keep the answer nowhere, the error ends with ``Run `claude`, sign in, then try again.`` instead.

With nothing behind the keychain, `stow` changes nothing. It prints `Nothing is left behind the store Claude Code keeps its login in, so there is nothing to put away.` On Linux it always prints that: the file is where Claude Code keeps its login.

```sh
pitboard stow --yes
```

```text
Parked the login /Users/you/.claude/.credentials.json held for `work`, then deleted the file.
It also held 1 other key, `mcpOAuth`, which went with the file: Pitboard does not move it, and Claude Code's document in the keychain keeps its own.
Once the file is gone, Claude Code sessions already running follow a switch within 33 seconds again, and one that signed in with its login, such as one over SSH, is signed out.
```

In the app, **Put Away** on the notice **A login file is left behind the keychain** does the same, as [Accounts pane](/reference/app#accounts-pane) lists.

## `abandon`

`pitboard abandon` deletes `~/.pitboard/journal.json`, the record of an [interrupted switch](/concepts/switching#interrupted-switches). It writes no login. Each tool keeps the login it has, and both accounts of the switch keep their parked logins.

For OpenAI's Codex CLI, it also drops a parked login that copies the login in use. [Why Codex logins are moved, not copied](/concepts/switching#why-codex-logins-are-moved-not-copied) says why.

While `CLAUDE_CODE_CUSTOM_OAUTH_URL` is set, `abandon` gives up only on a Codex switch. Otherwise it refuses with `custom_oauth_endpoint`, exit status 3.

```sh
pitboard abandon
```

```text
Gave up on the interrupted switch from work to personal. 2 login(s) kept; nothing was deleted. Run `pitboard` to see who is signed in.
```

With no interrupted switch, it prints `There is no interrupted switch to give up on.` and changes nothing.

[An interrupted switch cannot be finished](/troubleshooting/recovery#an-interrupted-switch-cannot-be-finished) says when to run it.

## `repair`

`pitboard repair` finds parked logins that Pitboard's account list does not name.

On macOS, it lists keychain items whose names start with `pitboard-park-`. Listing reads only names, so macOS does not ask for permission. On Linux, it lists files in `~/.pitboard/vault/`. It adds the names in `~/.pitboard/pending`, then reads each one the account list does not name.

Pitboard writes a parked login's name to `pending` before creating it. Every switch, enrolment, `forget`, `rename`, `stow` and `uninstall` resolves the names on that list as it starts, without listing the keychain. A parked login is missing from both only after `~/.pitboard` is lost or restored from a backup. That is when `repair` is needed.

Like `use`, it first finishes or undoes an interrupted switch, and stops if it cannot.

It gives a parked login back to the enrolled account whose id is in its name when:

- its refresh token has not expired
- the account holds no parked login, or `pending` names this one and the account holds an older one
- it is not a copy of the Codex login in use

| Output | When |
| --- | --- |
| `Gave personal back a parked login that nothing named.` | It gave a login back. One line per login |
| `Deleted 1 parked login(s) Pitboard wrote down here and nothing recorded.` | No account could take logins that `pending` names |
| `1 parked login(s) here belong to no account Pitboard knows and were not written down by this one. Left alone: the keychain is shared by the whole machine, and they may be another Pitboard's.` | No account could take logins that `pending` does not name |
| `1 could not be read this time and were left alone. Unlock the keychain and run this again.` | It could not read logins, as while the keychain is locked |
| `Every parked login here is accounted for.` | It found nothing to do |

On Linux, "keychain" in these lines means `~/.pitboard/vault/`, which no other Pitboard directory uses.

While `CLAUDE_CODE_CUSTOM_OAUTH_URL` is set, `repair` refuses with `custom_oauth_endpoint`, exit status 3.

[Pitboard lost track of parked logins](/troubleshooting/recovery#pitboard-lost-track-of-parked-logins) says when to run it.

## `adopt`

`pitboard adopt` takes over a Pitboard directory another computer wrote. Until you run it, commands that read the account list refuse that directory with `state_wrong_machine`.

It keeps every account with its label, email and remembered usage. It drops every parked login without asking Anthropic or OpenAI whether it still works. Asking means renewing the login, and nobody has measured whether that ends the other computer's copy. [What Pitboard will not do](/concepts/limits#rules) says why a parked login never moves between computers.

It leaves an interrupted switch for the next change to finish or undo.

```sh
pitboard adopt
```

```text
Took over this directory: 2 account(s) kept.
1 parked login(s) dropped, because a login belongs to the computer that signed in.
Sign in to each again:
  pitboard enroll personal --sign-in
```

If the directory is already this computer's, `adopt` prints `This Pitboard directory was already written on this computer.` and changes nothing.

[The Pitboard directory came from another computer](/troubleshooting/recovery#the-pitboard-directory-came-from-another-computer) says when to run it.
