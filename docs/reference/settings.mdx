  </Tab>
  <Tab title="Windows">
    Right-click Pitboard's icon in the notification area and select **Settings**, or select **Settings** at the foot of the Pitboard window's navigation pane (Ctrl+Comma). Settings is one page in the Pitboard window, with the sections **General**, **Limits**, **Advanced** and **About**.
  </Tab>

## General

| Control | System | Default |
| --- | --- | --- |
| **Open Pitboard at login** | macOS | Off |
| **Menu bar shows** | macOS | **Account and usage** |
| **Start when you sign in to Windows** | Windows | Off |

### Open Pitboard at login

On macOS, turned on, it adds Pitboard to macOS's login items. macOS may want your approval first, and Pitboard does not open at login until you give it. The pane then shows **macOS is waiting for you to allow Pitboard in Login Items.** and **Open Login Items Settings**.

If macOS refuses the change, its reason shows under the setting.

### Start when you sign in to Windows

On Windows, turned on, it writes the value `Pitboard` in your account's `Run` key, which starts Pitboard without its window when you sign in.

Where Windows' own **Startup** settings turned Pitboard off, the switch is dimmed and reads **Turned off in Settings > Apps > Startup, where you can turn it on again.** **Open Startup settings** under it opens that page. Pitboard reads the setting again each time Settings opens, and as you come back to the Pitboard window while it shows Settings.

### Notifications

On macOS, when Pitboard's notifications are turned off in **System Settings** > **Notifications**, **General** reads **Notifications from Pitboard are turned off in System Settings.** with **Open Notification Settings**, which opens that page. Pitboard reads it again each time Settings opens, and as you come back to the app.

On Windows, when Windows shows none of Pitboard's notifications, a **Notifications** card under **Start when you sign in to Windows** says why. Pitboard reads it again whenever it reads that switch's setting.

| Windows | The card reads |
| --- | --- |
| Pitboard's notifications turned off in **Settings** > **System** > **Notifications** | **Notifications from Pitboard are turned off in Settings > System > Notifications.** and **Open notification settings** |
| Every app's notifications turned off there | **Notifications are turned off for every app in Settings > System > Notifications.** and **Open notification settings** |
| Group Policy turns them off | **Group Policy turns off app notifications on this PC.** |
| Windows offers Pitboard none | **Windows offers this process no app notifications.** |
| Registering for notifications failed | The reason Windows gave |

### Menu bar shows

On macOS, Pitboard's item in the menu bar shows:

| Choice | The item shows |
| --- | --- |
| **Account and usage** | The label of the account in use and its percentage: **work 42%** |
| **Usage only** | The percentage: **42%** |
| **Icon only** | The Pitboard mark |

[Menu bar item](/reference/mac-app#menu-bar-item) says which account and which limit the percentage follows. On Windows, the icon's tooltip says the same, as [Icon in the notification area](/reference/windows-app#icon-in-the-notification-area) describes.

### Updates

<Tabs>
  <Tab title="macOS">
    A copy from a release download or the `pitboard-app` cask has these controls:

    | Control | Default | What it does |
    | --- | --- | --- |
    | **Check for updates automatically** | On | Checks GitHub for a newer version once a day. |
    | **Download and install updates automatically** | Off | Downloads an update in the background and installs it when Pitboard quits. Dimmed while the daily check is off. |

    **Check Now** checks at once, in the updater's own window. Beside it, the pane names your version, such as **Pitboard 0.10.0**. Once a daily check finds a newer one, it reads **Pitboard 0.10.1 is ready to install.** and Pitboard's [menu](/reference/mac-app#menu) offers **Install Pitboard 0.10.1**.

    A copy built from source has no update key and cannot update itself. In place of these controls, **General** shows **Version** and a note saying so.
  </Tab>
  <Tab title="Windows">
    A copy installed from a release has these controls:

    | Control | Default | What it does |
    | --- | --- | --- |
    | **Check for updates automatically** | On | Checks GitHub for a newer full release by itself. |
    | **Check now** | A button | Checks at once, in the updater's own window. |

    Beside **Check now**, the section names your version. Once a check finds a newer one, it reads **Pitboard 1.0.1 is ready to install.** and Pitboard's [menu](/reference/windows-app#menu) offers **Install Pitboard 1.0.1**.

    A beta finds only the next full release, and says so: **A beta updates itself to 1.0.0 once that is out. Install a later beta by hand.** Until a full release of Pitboard for Windows is out, a beta checks for nothing and says **No full release of Pitboard for Windows is out yet, so there is no update to check for.** It looks again each time Settings opens.

    A copy that cannot update itself, or a beta with nothing to check for, says why, has no **Check for updates automatically**, and dims **Check now**.
  </Tab>
</Tabs>

[What leaves your machine](/security#what-leaves-your-machine) lists what a check sends.

## Limits

| Control | Section | Default |
| --- | --- | --- |
| **When a limit reaches** | macOS: **Before an account runs out**. Windows: **Limits** | **Notify Me** |
| The share in it | macOS: a field and a stepper beside the choice. Windows: **Share of a limit**, under the choice | 95%, from 50% to 99% in steps of 1% |
| **From** | **Warm up limits** | 06:00 |
| **To** | **Warm up limits** | 22:00 |
| A switch for each Claude Code account | **Warm up limits** | Off |

The choice and its share are kept in `app.json`, as [The app](/reference/files#the-app) describes. Both stay dimmed until the app has read that file.

### When a limit reaches

While the app is open, it acts once a limit of the account in use reaches the share:

| Choice | What the app does |
| --- | --- |
| **Do Nothing** | Posts nothing. Pitboard's menu and window still offer a switch once the account runs out. |
| **Notify Me** | Posts one notification for each limit and reset, with **Switch** where another account of the tool is under the share in every limit. [Notifications](/reference/mac-app#notifications) lists its words. |
| **Switch Automatically** | Switches Claude Code, as [Switch before an account runs out](/guides/automatic-switching) gives the rules. It notifies of Codex as **Notify Me** does. |

On Windows, the choices are **Do nothing**, **Notify me** and **Switch automatically**, and the share is a number box from 50 to 99. The share is dimmed under **Do Nothing**. [`pitboard watch`](/reference/account-commands#watch) never reads this setting.

A note under the choice says what it does. Under **Switch Automatically**, it says when running sessions follow, as [Open sessions](/concepts/open-sessions) explains, and **Anthropic's terms may cover automatic switching and warm-ups.** follows with **Is this allowed?**, which opens [Is this allowed](/concepts/limits#is-this-allowed).

Under **Switch Automatically**, the app decides whether to switch:

- When you choose it or change the share.
- After each usage read.
- After another Pitboard run records a switch or usage.
- At least every 30 seconds.

A line says what the app last decided:

| Line | Shown when |
| --- | --- |
| **Watching work: 62% of its 5-hour limit, as of 16:40.** | No limit of `work`, the account in use, reached the share. |
| The same, then **Anthropic holds Pitboard off asking again until 17:40.** | Anthropic told Pitboard to wait. |
| **work has used 97% of its 5-hour limit. Pitboard tries again at 16:41.** | A try at this limit failed a moment ago. |
| **work has used 97% of its 5-hour limit. Pitboard isn't switching:**, then the reason | Pitboard holds back. **It decides again at 16:45.** follows while `work` has been in use under 5 minutes. |
| **Pitboard isn't switching Claude Code:**, then the reason | Pitboard cannot decide. **It asks again at 16:41.** follows while it cannot identify Claude Code's login. |
| **Pitboard could not switch Claude Code, and tries again at 16:41:**, then the error | A switch failed. |
| **Pitboard cannot tell whether to switch Claude Code:**, then the error | Pitboard could not read its own files. |
| **Switched Claude Code from work to personal: work has used 97% of its 5-hour limit.** | The app switched. |

[Automatic switching](/reference/automatic-switching) lists each reason. The [menu bar app](/reference/mac-app#notifications) and [the app on Windows](/reference/windows-app#notifications) list what they post.

### Warm up limits

While the app is open, it warms up each Claude Code account turned on here, between **From** and **To** each day, as [Warm up accounts](/guides/warm-up) describes. `pitboard warm` changes the same setting, and `pitboard watch` reads it.

**To** at 00:00 is the end of the day. A **From** later than **To** runs past midnight.

Under the list, **Anthropic's terms may cover automatic switching and warm-ups.** sits with **Is this allowed?**, which opens [Is this allowed](/concepts/limits#is-this-allowed).

Each account's row shows where its warm-up stands while it is on. A line under the list says what comes next:

| Line | Shown when |
| --- | --- |
| **Next warm-up: work at 14:50.** | An account is turned on, and this is the soonest it warms up. |
| **Warming up work now.** | That warm-up is due or under way. |
| **The last warm-up came to nothing:**, then the error | A warm-up the app made by itself failed. It shows until the next one starts a period or finds nothing due. |
| Why the setting cannot be read, such as **Which accounts Pitboard warms up, at …, can't be read** | `warm.json` cannot be read. |
| **Pitboard isn't warming up accounts:**, then the reason | Nothing can be warmed up here, for a reason in the second table of [When it holds back](/guides/warm-up#when-it-holds-back). |

On Windows, the line sits under **Warm up limits** and its hours, and shows while the section is closed.

## Advanced

### Renew parked logins daily

Off by default. A note under it says what daily renewal does. Once a Claude Desktop account is enrolled on macOS, the note ends **A parked Claude Desktop login is never renewed.**

It has the system's scheduler run `pitboard renew` once a day, with the command line that came with the app. That run renews due parked logins and nothing else. [Keep parked logins alive](/guides/renewal) says why.

The setting is on whenever the scheduler has the job, including one `pitboard schedule install` made. `pitboard schedule status` says where the job is, as [Renewal schedule](/reference/files#renewal-schedule) names it. A change that fails says why under the setting.

You can always turn it off. You cannot turn it on in these cases:

| Case | System | The pane shows |
| --- | --- | --- |
| macOS runs the app from a temporary copy | macOS | Dimmed, with a note that starts **Move Pitboard to your Applications folder first.** |
| No command line that can run came with the app, as in a build run from Xcode or from its build folder | macOS, Windows | Dimmed, with **This copy of Pitboard has no command line inside it to run on a schedule.** |
| `PITBOARD_HOME` names a directory other than [the default one](/reference/files#the-pitboard-directory) | macOS, Windows | A refusal under the setting: the schedule renews only the parked logins in the default directory. |

### Command line

**In your terminal** shows the path of the `pitboard` a terminal would run, or **Not installed**. A note under it says how that `pitboard` updates:

| The `pitboard` found | Note |
| --- | --- |
| The one that came with the app, directly or through a link | **The one inside this app, so it updates with the app.** |
| Any other | **Installed apart from this app, so update it the way you installed it.** |

<Tabs>
  <Tab title="macOS">
    Pitboard looks on your login shell's `PATH`, skipping folders that need your permission, such as `~/Documents`. It then looks in `~/.cargo/bin`, `~/.local/bin`, `/opt/homebrew/bin` and `/usr/local/bin`.

    **Install Command Line Tool** shows only when Pitboard finds no `pitboard` and the app's own command line can run. After macOS asks for an administrator's password, it links `/usr/local/bin/pitboard` to `Pitboard.app/Contents/Helpers/pitboard`. It replaces a link already there.

    | Case | The pane shows |
    | --- | --- |
    | macOS runs the app from a temporary copy | No button, and a note that starts **Move Pitboard to your Applications folder first.** |
    | A file, not a link, is at `/usr/local/bin/pitboard` | `/usr/local/bin/pitboard` **is already there and is not a link, so it was kept.** |
    | You cancel the password prompt | Nothing |
    | Any other failure | The reason macOS gives, or **The link could not be made.** |
  </Tab>
  <Tab title="Windows">
    Pitboard looks on the `PATH` your account and the machine set, then in `.cargo\bin` in your profile folder, then in `bin` in the app's folder, then where npm, WinGet and Scoop put programs.

    The installer puts the command line on your `PATH`, so the section has no install button. With none found, the note reads **Pitboard's installer puts pitboard on your PATH, which terminals opened after it ran see.**
  </Tab>
</Tabs>

## About

On Windows, **About** shows Pitboard's version and links to usepitboard.com, **Pitboard help**, the source code on GitHub, **Report a problem** and the Apache License 2.0. On macOS, **About Pitboard** in Pitboard's menu shows the version.
