title: "Security and privacy"
description: "Pitboard keeps parked logins on your machine, sends them only to the service that issued them, and has no telemetry."
---

Pitboard moves and stores the OAuth refresh tokens of Claude Code and OpenAI's Codex CLI. Each grants full access to a paid account. [SECURITY.md](https://github.com/datlechin/pitboard/blob/main/SECURITY.md) is the full policy.

## Where parked logins are kept

On macOS, parked logins are keychain items whose names start with `pitboard-park-`. Pitboard reads and writes them, and Claude Code's item, only through `/usr/bin/security`, the one program that item trusts. On macOS 26, an item written through the Security framework takes about a second for each read by `security`, against 0.01 seconds.

A Claude Code parked login holds the OAuth block and the account's other fields, such as `trustedDeviceToken`. Whether restoring a device token spares a re-verification has not been measured. A Codex parked login is the whole `auth.json`. As read in Codex 0.154.0, that file can also hold an OpenAI API key.

On Linux, parked logins are files in `~/.pitboard/vault/`, at mode 0600 in a 0700 directory. Claude Code keeps its own login in a plaintext `~/.claude/.credentials.json`, as [Claude Code files](/reference/files#claude-code-files) lists. Any process running as you can read both.

`pitboard doctor` fails if anyone else has access to the vault or Claude Code's file. For Codex's `auth.json`, it warns.

Of Pitboard's other files, only `signin/` holds a login, while a sign-in runs: see [The Pitboard directory](/reference/files#the-pitboard-directory).

## Where account windows keep their data

Each [account window](/guides/account-windows) keeps its site's cookies, storage and caches, sign-in included, in a WebKit store of its own. WebKit keeps it in files under your `~/Library`, as a browser does. A renamed account keeps its store. [Account windows](/reference/files#account-windows) gives the paths.

Pitboard never reads or copies what a site keeps there, and adds no script to a page. It never signs a window in with a Claude Code or Codex login.

The app records each store and each window's last page in `windows.json`, a file only you can read. It makes a store when the account's window first opens. **File** > **Remove Website Data** wipes the store and signs the window out on this Mac only. Forgetting the account deletes its store at the app's next successful read of the accounts.

The app deletes a store only when its own Pitboard directory recorded it and no other existing one did. A copy run with another `HOME` or `PITBOARD_HOME` therefore signs no other copy's windows out. While the app cannot read `windows.json`, it deletes no store.

## Links shared from a browser

Pitboard's Share extension takes the one web address a browser shares and checks that it is a claude.ai or chatgpt.com page. It hands the address to its app as a `pitboard://open?url=` link and keeps nothing. It is sandboxed, with no network, file or shared-folder access.

Anything on your Mac can open such a link, so the app checks it again and opens nothing until you choose an account. It refuses the sites' sign-in links: one would sign the window in as whoever it belongs to. [Refused links](/reference/account-windows#refused-links) lists them.

## Anthropic terms

Anthropic's [Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance#authentication-and-credential-use) page says, as read on 4 October 2026:

> Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow.

A claude.ai window signs in on claude.ai's own pages. WebKit keeps the sign-in's cookies under Pitboard's bundle identifier. Whether Anthropic counts that under the clause is not known.

## What leaves your machine

Pitboard has no server of its own and makes only these requests:

| Request | Carries | Used for |
| --- | --- | --- |
| `api.anthropic.com/api/oauth/profile` | An access token | Identifying a Claude Code login |
| `api.anthropic.com/api/oauth/usage` | An access token | A Claude Code account's usage |
| `platform.claude.com/v1/oauth/token` | A refresh token and the client id it was issued to | Renewing a Claude Code parked login, or one `pitboard stow` puts away |
| `chatgpt.com/backend-api/wham/usage` | An access token and the ChatGPT account id | A Codex account's usage, and checking a login before a switch to it |
| `auth.openai.com/oauth/token` | A refresh token and Codex's client id | Renewing a Codex parked login |
| claude.ai, chatgpt.com, their sign-in pages and what their pages load | What the site keeps in that window | An account window, through WebKit |
| `github.com/datlechin/pitboard/releases` | Nothing of yours | The app's update check and downloads: see [Updates](/reference/settings#updates) |

The command line never checks for updates.

Only [`pitboard stow`](/reference/recovery-commands#stow) renews a login a tool may be using: one it puts away with an expired access token. It holds [Claude Code's renewal locks](/reference/files#claude-code-files) meanwhile.

Pitboard's own requests verify TLS against your system's trust store and time out after 5 seconds.

They go through the HTTP or HTTPS proxy that the [proxy variables](/reference/files#environment-variables) name. The proxy sees each request's host, not what it carries.

A company proxy whose root certificate your system trusts can decrypt each request, tokens included.

While the variables name a SOCKS proxy, each request `NO_PROXY` does not exempt fails before anything is sent.

The daily renewal job keeps the proxy variables it was installed with, passwords included, in files only you can read. On Linux, systemd also hands them to programs that ask, as systemd.exec(5) says.

## Large logins on macOS

Pitboard hands a login to `security` in hex on standard input, where `ps` cannot see it. That input stays within 4032 bytes, Claude Code's own ceiling as read in 2.1.284: about 2 KB of login.

MCP server tokens can push a Claude Code login past that. Every Codex parked login is past it.

Past it, Pitboard passes the login as an argument. Another process running as you could read it while the call lasts. A switch, a `--sign-in` enrolment or `pitboard stow` that does this says so. A renewal does not.

With `PITBOARD_NO_ARGV=1`, Pitboard refuses such a write. It then parks no Codex account, and leaves a parked login that size unrenewed.

Opened from Finder or at login, the app lacks your shell's `PITBOARD_NO_ARGV`. A renewal schedule installed while it is set keeps it.

## What Pitboard protects against

- Pitboard identifies each login before moving it.
- The next command that changes something finishes or undoes an interrupted switch: see [Interrupted switches](/concepts/switching#interrupted-switches).
- No parked login goes untracked: Pitboard records its name before storing it and retries a failed delete.
- A locked keychain reads as unreadable, never as empty.
- Pitboard keeps no copy of a login in use.
- Pitboard refuses a synced folder for its directory: a parked login belongs to one machine.
- An account window stays on its site and sign-in pages, and sends other pages to your browser.
- An account window stops Google's sign-in, which in your browser would sign in the browser.
- WebKit quarantines every download from an account window: see [Downloads](/reference/account-windows#downloads).
- Every release is attested: see [Verify a download](/install/verify).
- The app installs an update signed with its update key.
- A copy signed with a Developer ID also installs one signed by the same team.
- The release workflow refuses to change the update key without a declared rotation.

## What Pitboard does not protect against

- Another process running as you, which can read each account window's data as it can a browser's.
- The sites' own pages, which run in WebKit as they would in a browser.
- Another user with administrator access to your computer.
- Anyone who can already read your files.
- A compromised Claude Code, Codex or library Pitboard uses.
- Signing out in anything that ran Codex before a switch, which revokes the login Pitboard parked: see [What happens to open sessions](/guides/switch#what-happens-to-open-sessions).
- An account you no longer use, whose parked login Pitboard keeps renewing: see [Accounts you no longer use](/guides/renewal#accounts-you-no-longer-use).
- A deleted parked login, which stays valid until it expires. Pitboard revokes no login.

CI checks Pitboard's Rust libraries for known advisories, and Sparkle, the app's updater, only for a newer release.
