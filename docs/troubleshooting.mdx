Start with `pitboard doctor`. For an interrupted switch, lost parked logins or a directory from another computer, see [Recover after a crash, a restore or a move](/troubleshooting/recovery). For other messages, see [Error and warning codes](/reference/errors).

## Check first

`pitboard doctor` checks what Pitboard relies on and marks each check `✓` (holds), `!` (worth a look) or `✗` (broken). Its last line is one of these:

```text
Everything Pitboard checks is in order.
2 things are worth looking at.
1 broken: do not switch accounts until fixed.
```

`pitboard log` lists Pitboard's last 20 changes and how each ended.

In the app, click Pitboard's item in the menu bar, then choose **Open Pitboard**. The window's **This Mac** pane makes the same checks and heads them with the same line, and **Activity** shows the log.

For every check, see [Maintenance commands](/reference/maintenance-commands#doctor).

## A parked login has expired

`pitboard status` shows `login expired` beside a Claude Code account, and Pitboard's menu shows **Needs signing in again**. Pitboard renews [parked logins](/concepts/switching#parked-logins) only when it runs, so a Claude Code one left for weeks expires.

To fix it, see [Sign in to an account again](/guides/sign-in-again). To prevent it, see [Keep parked logins alive](/guides/renewal).

## Pitboard cannot confirm which account is signed in

If the message says `Pitboard could not confirm`, check the connection and run the command again.

If it also says `Pitboard does not use SOCKS proxies yet, and ALL_PROXY names one`, the variable it names holds a SOCKS proxy's address. Pitboard does not go through SOCKS proxies, and sends nothing around one. Set that variable to an HTTP proxy's address, or unset it, then run the command again. `pitboard doctor` names the proxy on its `network` line.

If it says `session has expired`, run the program it names once, then run the command again.

## Claude Code still shows the previous account

An open Claude Code session follows a switch within about 33 seconds. If not, the switch may have warned why:

```text
warning: ANTHROPIC_API_KEY in the environment is set, so Claude Code signs in with it and not with the login Pitboard moved. Unset it for the switch to take effect.
```

Unset or remove what it names, then restart Claude Code.

If the warning says Claude Code's config could not be updated, the switch worked, but the old name may show until the next switch.

A session started over SSH, or one where the keychain is locked, does not follow a switch. See [Claude Code over SSH uses another account](#claude-code-over-ssh-uses-another-account).

If the switch said that open sessions keep their account until their login is next renewed, `~/.claude/.credentials.json` is behind the keychain. Each session follows when it next renews its login, or when you start it again. To have sessions follow within 33 seconds again, delete the file as the same section says.

## A running codex still uses the old account

A running `codex` keeps its account until you restart it. To do that without losing a login, see [Switch accounts](/guides/switch#what-happens-to-open-sessions).

## Pitboard refuses Codex's login store

Pitboard switches OpenAI's Codex CLI only when Codex keeps its login in `auth.json` and signs in with ChatGPT; see [Use Pitboard with Codex](/guides/codex#before-you-enrol-a-codex-account).

## Usage shows old numbers

Old numbers say when they were measured, as in `measured 14:02, 1m ago`, and may give a reason. For Codex, read OpenAI for Anthropic:

| Reason | Cause and fix |
| --- | --- |
| No reason | Pitboard asked moments ago. For an account with a five-hour limit, it does not ask again for 3 minutes. To ask anyway, run `pitboard status --fresh` or choose **Refresh** in Pitboard's menu. |
| `Anthropic is rate limiting usage checks` | Anthropic asked for fewer requests. Pitboard waits, then asks again. `--fresh` and **Refresh** wait too. |
| `Anthropic could not be reached` | Check the connection. Pitboard waits, then asks again. |
| `Anthropic answered with an error; try again later` | Anthropic returned an error. Pitboard waits, then asks again. |

For why Pitboard waits, see [How usage is read](/concepts/usage#how-often-pitboard-asks).

## macOS says the keychain is locked

Where macOS cannot show a password prompt, as over SSH, a locked keychain stops Pitboard with the error `credential_store_locked`:

```text
the keychain is locked and cannot ask to be unlocked from here; unlock it with `security unlock-keychain`, or run Pitboard from a desktop session
```

Do what the message says. If a switch was stopped, run it again: Pitboard first finishes or undoes it.

`pitboard doctor` fails its `credential` check once and marks each parked login `not read: the keychain is locked`. Nothing is wrong with those logins, so do not sign in to them again.

As read in Claude Code 2.1.294, a session keeps the login it last read while the keychain is locked, and follows no switch. One started then signs in with `.credentials.json`, or is signed out.

## Claude Code over SSH uses another account

A Claude Code session started over SSH can use another account than the one Pitboard shows, and stay on it after every switch. `pitboard doctor` warns with `fallback login`, and each `pitboard status` without `--offline`, each read in the app and each change warns with `fallback_login`.

The cause is a `/login` run where the keychain was locked. As read in Claude Code 2.1.294, it writes the login to `~/.claude/.credentials.json` and leaves the keychain's in place. Claude Code deletes that file only when it writes the keychain while the keychain is empty, so the file outlives every switch. A session that cannot read the keychain signs in with the file.

While the file is there, sessions that read the keychain also stop following a switch within 33 seconds. Each keeps its account until its login is next renewed, or until it is started again. A file with no login in it, such as `{}`, does the same, and `pitboard doctor` says `no login in it`. So does a file Pitboard cannot read, and `pitboard doctor` says why.

To have one login everywhere:

<Steps>
  <Step title="Delete the file">
    Run `rm ~/.claude/.credentials.json`, or the path the warning names. A session that was using it is signed out. Open sessions that read the keychain follow the next switch within 33 seconds.
  </Step>
  <Step title="Reach the keychain">
    Run `security unlock-keychain ~/Library/Keychains/login.keychain-db` in the same session, or start the session from a desktop terminal. It then uses the account Pitboard switched to.
  </Step>
</Steps>

Do not run `/login` while the keychain is locked: it leaves the file again.

## Pitboard cannot find Claude Code

Without `claude`, a Claude Code sign-in stops like this:

```text
error: `claude` is not on this machine, and Pitboard signs in with Claude Code's own sign-in. Install Claude Code, or point Pitboard at it.
```

Install Claude Code, then run `claude` once and sign in. If `claude` is installed, add its folder to your `PATH`.

The app looks for `claude` only when it opens: on your login shell's `PATH`, then in `~/.local/bin`, `/opt/homebrew/bin` and `/usr/local/bin`. After you install Claude Code, quit Pitboard and open it again.

## Pitboard does not open at login

Pitboard opens at login only when **Open Pitboard at login** is on in **Settings** > **General**. If macOS is waiting for you there, click **Open Login Items Settings** and allow Pitboard.

## Daily renewal stopped working

`pitboard doctor` fails its `renewal schedule` check with `which is not there any more`. The app moved, or the Pitboard the schedule ran was removed.

Turn **Renew parked logins daily** off and on in **Settings** > **General**, or run:

```sh
pitboard schedule uninstall
pitboard schedule install
```

### The schedule's proxy differs

`pitboard doctor` warns with `renewal schedule's proxy` when daily renewal goes through another proxy than the one your shell names, or through none. Daily renewal keeps the proxy it was installed with. From a shell where the proxy variables are as you want them, run:

```sh
pitboard schedule install
```

The app's **This Mac** pane shows the same line without a warning. The app compares with its own proxy variables, which macOS gives it, and those name no proxy unless `launchctl setenv` set one. Turning **Renew parked logins daily** off and on in the app gives daily renewal the app's variables, so it would drop a proxy that a shell gave it.

## A file was written by a newer Pitboard

The Pitboard you ran is older than another using the same files. Update it: see [Update Pitboard](/install#update-pitboard).

## Pitboard refuses a folder that syncs

Pitboard refuses to keep its files, `~/.pitboard` or `PITBOARD_HOME`, in a folder that syncs to other machines, such as Dropbox or iCloud Drive. Parked logins belong to one machine. Set `PITBOARD_HOME` to a local folder. For the names Pitboard refuses, see [Files and environment variables](/reference/files#the-pitboard-directory).

## Pitboard changes nothing as root

Run as root or with `sudo`, Pitboard refuses every command that changes something, with the error `elevated`. This includes a container or a WSL distribution whose only user is root. A file Pitboard made as root would belong to root, and a keychain item might too, so your own runs might not read or replace it.

`pitboard status` and the status line still answer, from what Pitboard last measured, and renew and write nothing. `pitboard doctor` fails its `elevated` check. Run Pitboard as yourself, without `sudo`.

### `SUDO_UID` is set in your own shell

Pitboard takes a run as one with `sudo` when `SUDO_UID` is set and not empty, as `sudo` sets it. A shell started with `sudo -iu` and your own name passes `SUDO_UID` to everything started from it, such as a tmux server or an editor's server. Pitboard run from there refuses, though it runs as you.

If `id -un` prints your own name, run the command without `SUDO_UID`:

```sh
env -u SUDO_UID pitboard use work
```

To stop it for good, start the shell, tmux or the editor again without `sudo`.

### Remove what Pitboard made as root

Pitboard 0.7.0 and earlier ran as root and with `sudo`. `pitboard schedule uninstall` and `pitboard uninstall` refuse to remove what it made that way, so remove it by hand from a root shell: as root, or after `sudo -i`.

On Linux, turn off the daily renewal schedule, delete its files, then delete Pitboard's directory:

```sh
systemctl --user disable --now pitboard-renew.timer
rm ~/.config/systemd/user/pitboard-renew.service ~/.config/systemd/user/pitboard-renew.timer
rm -r ~/.pitboard
```

On macOS:

```sh
launchctl bootout gui/$(id -u)/com.datlechin.pitboard.renew
rm ~/Library/LaunchAgents/com.datlechin.pitboard.renew.plist
rm -r ~/.pitboard
```

Where no schedule runs, `systemctl` or `launchctl` says so; go on to the next command. If `PITBOARD_HOME` named another directory, delete that one. Deleting the directory deletes the parked logins kept in it, except on macOS, where they are in the keychain, as [Remove Pitboard](/install/remove#delete-parked-logins-and-pitboard%E2%80%99s-files) says.

In a root shell, `~` is root's home. Under `sudo`, Pitboard used the home `sudo` passed on, which can be yours. Pitboard has not measured which home that is, or which keychain `security` wrote to as root. Look in your own as well, writing your home by its path, such as `/Users/me`.

## Account windows

These problems happen in an [account's window](/guides/account-windows), the claude.ai or chatgpt.com window the app opens for an account.

### Google's sign-in is refused

Google does not allow its sign-in pages inside apps, so the window stops them and says so. It does not send them to your browser, where they would sign in your browser instead.

Sign in with the account's email address, as the note at the top of the window says. For the steps on each site, see [Sign in](/guides/account-windows#sign-in).

For the same reason, Gmail, Google Drive and Google Calendar cannot be connected in the window. claude.ai's Google single sign-on does not work there either.

### A passkey does not work

Passkeys do not work in an account's window. macOS gives passkeys to a web page only in an app it lets act as a browser, and Pitboard is not one. On chatgpt.com, sign in with the password or the code chatgpt.com emails you.

### Pitboard is missing from the Share menu

In Safari, the Share menu is the toolbar's **Share** button or **File** > **Share**. In Chrome and Firefox, it is **File** > **Share**. If **Pitboard** is not listed there, turn it on in System Settings:

- macOS 15 and later: **System Settings** > **General** > **Login Items & Extensions** > **Sharing**.
- macOS 14: **System Settings** > **Privacy & Security** > **Extensions** > **Sharing**.

Whether other browsers list Pitboard is not known. If your browser has no Share menu, open the account's window and go to the page there.

### An account's window does not load its page

When a page does not load, the window shows **Couldn't Load the Page** with the reason, such as a lost connection. Fix what the reason names, then click **Try Again**.

A page that stops working is loaded again. If it stops again within 60 seconds, the window shows **Couldn't Load the Page** and **The page stopped working.**

The window sends WebKit's own user agent. Whether the sites' checks for automated traffic ever stop it is not known.

### Downloads are not saved

An account's window saves downloads in your Downloads folder. The first time, macOS may ask whether Pitboard can use that folder. If you clicked **Don't Allow**, open **System Settings** > **Privacy & Security** > **Files & Folders** and turn on **Downloads Folder** for Pitboard.

A download that fails shows why in the window's **Downloads** list, which the toolbar's **Downloads** button opens.

### An account's window is signed in as the wrong account

Pitboard cannot see which account a window is signed in to, because it never reads what the window keeps. The window's title is the label of the account it belongs to, whoever signed in. To start again:

<Steps>
  <Step title="Remove the window's data">
    With the window in front, choose **File** > **Remove Website Data**.
  </Step>
  <Step title="Confirm">
    Click **Remove**. The window signs out and starts again at the site's home, with a note that names the email address to sign in as.
  </Step>
  <Step title="Sign in">
    Sign in as that email address. See [Sign in](/guides/account-windows#sign-in).
  </Step>
</Steps>

Removing the data does not tell the site, so neither account is signed out anywhere else.

## Report a problem

Open a [GitHub issue](https://github.com/datlechin/pitboard/issues/new/choose) with:

- What you ran, what it printed and what you expected.
- The output of `pitboard --version`, `pitboard doctor --json` and the last lines of `pitboard log`.
- How you installed Pitboard, and your macOS or Linux version.

`pitboard doctor --json` hides email addresses, account identifiers and your home folder; plain `pitboard doctor` does not.

For a security problem, see [Security and privacy](/security#report-a-vulnerability).
